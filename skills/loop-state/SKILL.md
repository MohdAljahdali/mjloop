# Loop State

## Layout

```
.loop/
├── config.yaml      tracks, limits, verify commands — hand-editable
├── state.json       current run — MCP-owned, never hand-edited
├── INDEX.md         every plan and its status — generated by loop_index_render
├── runs/<run>/      HALT.md, and per cycle:
│   └── cycle-NN/    roster.json, <agent>.json, findings.json
├── plans/<plan>/    one directory per plan
│   ├── PLAN.md      the plan itself — prose, authored
│   ├── REVIEW.md    plan-critic's objections — prose, authored
│   ├── manifest.json  derived from the story files — MCP-owned
│   └── stories/     one markdown file per story, written through the tools
└── memory/          decisions and lessons (later milestones)
```

A run directory is named `<run_id>--<story|adhoc>--<track>`, and
`state.history[-1].ref` holds the path — that is what a story's `evidence` points at.

`PLAN.md` carries the plan's identity and its approval decision in frontmatter, with the
plan itself as prose below. `REVIEW.md` is `plan-critic`'s output. Both are authored;
`manifest.json` is derived.

## One owner

`state.json` and every `manifest.json` are written **only** by the loop MCP server. A
`PreToolUse` hook denies `Write` and `Edit` on them. This is not ceremony: a model
corrupting that JSON loses the entire run, and it is the most common way agent loops
fail in practice.

`config.yaml` is the opposite — it is yours. Edit it freely to change a track's cap,
force a specialist, or set verify commands.

Story files sit between the two. They are prose, so no hook denies a write to one, but
they are still tool-owned: `loop_story_add` and `loop_story_update` regenerate the plan's
manifest as part of the write, and a hand-edited story leaves the derived state behind.

## Tools

| Need | Tool | Writes |
|---|---|---|
| Provision `.loop/` | `loop_init` | the directories, `state.json`, `config.yaml` |
| Read the current run | `loop_state_get` | — |
| Open a run | `loop_run_start` | `state.json`, the run directory |
| Declare the cycle's agents | `loop_roster_set` | `cycle-NN/roster.json` |
| Persist an agent result | `loop_run_log` | `cycle-NN/<agent>.json`, `state.json` |
| Close a cycle | `loop_cycle_advance` | `state.json`, `cycle-NN/findings.json`, `HALT.md` |
| Stop with a report | `loop_halt` | `state.json`, `HALT.md` |
| Create a plan | `loop_plan_create` | `plans/<plan>/PLAN.md`, its `manifest.json` |
| Record a plan approval | `loop_gate_set` | `plans/<plan>/PLAN.md` frontmatter |
| Add a story | `loop_story_add` | the story file, its plan's `manifest.json` |
| Change a story | `loop_story_update` | the story file, its plan's `manifest.json` |
| Read a story, or resolve `--next` | `loop_story_get` | — |
| Rebuild the index | `loop_index_render` | `INDEX.md`, every `manifest.json` |

Nothing else refreshes `INDEX.md`. A story write regenerates its own plan's manifest, so
call `loop_index_render` after one if the index is to stay true.

`loop_state_get` returns a compact summary rather than the whole file, so the leader's
context does not grow with the cycle count. Read the run directory when you need detail.

## Reading a halted run

`.loop/runs/<run>/HALT.md` carries the reason, the cycles attempted, the open findings,
and the recommended next step. Read it before restarting anything.
