# Loop State

## Layout

```
.mjloop/
├── config.yaml      tracks, limits, verify commands — hand-editable
├── state.json       current run — MCP-owned, never hand-edited
├── INDEX.md         every plan and its status — generated by mjloop_index_render
├── design-system.md what the product looks like — authored, absent until synced
├── runs/<run>/      verify-pinned.json, map.md, HALT.md, and:
│   ├── cycle-NN/    roster.json, <agent>.json, findings.json, handoff.md,
│   │                evidence/ spilled excerpts, verify/ logs and index.json
│   └── closing/     roster.json, <agent>.json, verify/ — the run-closing pass
├── profile/         the project's component map — engine-owned, never hand-edited
│   ├── proposed.json  what the last scan found — overwritten by the next one
│   └── accepted/      rev-001.json, rev-002.json … immutable numbered revisions
├── plans/<plan>/    one directory per plan
│   ├── PLAN.md      the plan itself — prose, authored
│   ├── REVIEW.md    plan-critic's objections — prose, authored
│   ├── manifest.json  derived from the story files — MCP-owned
│   └── stories/     one markdown file per story, written through the tools
└── memory/          decisions, lessons and patterns — written by mjloop_memory_add
```

A run directory is named `<run_id>--<story|adhoc>--<track>`, and
`state.history[-1].ref` holds the path — that is what a story's `evidence` points at.

`PLAN.md` carries the plan's identity and its approval decision in frontmatter, with the
plan itself as prose below. `REVIEW.md` is `plan-critic`'s output. Both are authored;
`manifest.json` is derived.

`design-system.md` is extracted from the project by `/mjloop:design-sync`, never generated
and never created at init. It is authored: correct it by hand when the extraction got
something wrong, and re-sync when the code moves.

## What a run leaves behind

A run keeps what it learned in files beside the state rather than in fields inside it, and
each of those files has exactly one writer. Which tool that is decides where a correction
belongs, so it is worth knowing.

**`verify-pinned.json`** is the run's frozen copy of `config.yaml`'s `verify:` block — the
commands, the ceiling, and the failure patterns. `mjloop_run_start` writes it once, at run
start; `mjloop_verify_run` is its only reader. It is protected by basename exactly as
`state.json` is, so the `PreToolUse` hook denies a `Write` or an `Edit` to it in any run
directory of any project. The consequence is the one a person actually notices: an edit to
`verify:` takes effect at the **next** run start, never in the run that is open. What the
engine executes during a run is decided once, and nothing the run itself writes can change
it. A run that has lost its pin refuses to verify rather than falling back to the live
file — falling back would make deleting one file a way to choose what the engine runs.

**`map.md`** is the run's map of the ground. `mjloop_run_log` writes it from the passing
result of the agent the track's `map.drafted_by` names — no second pass and no model call.
A later mapping agent appends a section rather than overwriting the first, and the header
says later sections win, because the run changes the tree it mapped. `mjloop_state_get`
reports the path, so the leader carries it into a brief without listing the directory.

**`cycle-NN/handoff.md`** is the cycle's own record: each agent's status and summary, the
roster's skip reasons, the files touched, the verify table, and the findings still open.
`mjloop_cycle_advance` generates it from what the cycle already produced, after the state
transition has committed. Every section has a ceiling and names where the rest is, and a
failed write costs the handoff rather than the advance — every fact in it is still in the
per-agent files.

**`cycle-NN/verify/`** is what the engine itself executed: the whole output of each
invocation in `<slot>.log`, and `index.json`, the ledger of what ran and how it exited.
`mjloop_verify_run` writes both. The ledger is why `mjloop_run_log` can refuse a `pass`
whose evidence names a command the engine recorded as failing, killed, still running or
still queued.

**`cycle-NN/evidence/`** holds the tail of any excerpt longer than the stored ceiling,
written by `mjloop_run_log` before the result that points at it. Every truncation names
where the rest is — but not always here. When the entry's `ref` matches a command the
engine ran, the marker names that command's `verify/<slot>.log` instead and no tail file
is written: the log carries the command's whole output, which is strictly more than the
tail, but not the sentences the agent composed around it.

**`closing/`** is the run-closing pass — `roster.json` from `mjloop_roster_set`, one
`<agent>.json` per closing agent from `mjloop_run_log`, and `verify/` when a closing agent
re-ran a command. It sits outside every `cycle-NN/`, because those results belong to no
cycle and must not reach a verdict that has already been given.

## One owner

`state.json`, every `manifest.json` and every run's `verify-pinned.json` are written
**only** by the loop MCP server. A `PreToolUse` hook denies `Write` and `Edit` on them.
This is not ceremony: a model corrupting that JSON loses the entire run, and it is the most
common way agent loops fail in practice. The pin is on that list for a second reason — it
is the string the engine hands to a shell, so a run that could rewrite its own pin could
choose what the engine runs on its behalf.

Everything under `profile/` is denied the same way, by directory rather than by basename:
`rev-NNN.json` is a family of names and no list of them could cover the revision a project
has not written yet. An accepted revision is immutable because a run may have been routed
by it, and `proposed.json` is protected for a different reason — it is what an ordinary
acceptance reads, so a hand-edited proposal puts a component map nobody scanned in front
of the person accepting it. Both records are read by an acceptance and neither may be
reached by hand: `profile accept` takes the proposal, and `profile accept --from <revision>`
takes an accepted revision instead. Use `mjloop-cli profile show`, then `profile accept` or
`profile reject`.

`config.yaml` is the opposite — it is yours. Edit it freely to change a track's cap,
force a specialist, or set verify commands. Only the timing is worth remembering: a change
to `verify:` reaches the engine at the next run start, because a run executes its own
pinned copy of that block and reports the live one beside it rather than obeying it.

Story files sit between the two. They are prose, so no hook denies a write to one, but
they are still tool-owned: `mjloop_story_add` and `mjloop_story_update` regenerate the plan's
manifest as part of the write, and a hand-edited story leaves the derived state behind.

## Tools

| Need | Tool | Writes |
|---|---|---|
| Provision `.mjloop/` | `mjloop_init` | the directories, `state.json`, `config.yaml` |
| Read the current run | `mjloop_state_get` | — |
| Open a run | `mjloop_run_start` | `state.json`, the run directory, `verify-pinned.json` |
| Declare the cycle's agents | `mjloop_roster_set` | `cycle-NN/roster.json`, or `closing/roster.json` |
| Persist an agent result | `mjloop_run_log` | `cycle-NN/<agent>.json`, `state.json`, `map.md`, an evidence spill; `closing/<agent>.json` once the run is done |
| Run a verify command | `mjloop_verify_run` | `cycle-NN/verify/<slot>.log`, `cycle-NN/verify/index.json` |
| Close a cycle | `mjloop_cycle_advance` | `state.json`, `cycle-NN/findings.json`, `cycle-NN/handoff.md`, `HALT.md` |
| Stop with a report | `mjloop_halt` | `state.json`, `HALT.md` |
| Create a plan | `mjloop_plan_create` | `plans/<plan>/PLAN.md`, its `manifest.json` |
| Record a plan approval | `mjloop_gate_set` | `plans/<plan>/PLAN.md` frontmatter |
| Add a story | `mjloop_story_add` | the story file, its plan's `manifest.json` |
| Change a story | `mjloop_story_update` | the story file, its plan's `manifest.json` |
| Read a story, or resolve `--next` | `mjloop_story_get` | — |
| Rebuild the index | `mjloop_index_render` | `INDEX.md`, every `manifest.json` |
| Record a memory | `mjloop_memory_add` | `memory/<id>-<slug>.md` |
| Search memory | `mjloop_memory_search` | — |
| Read a memory | `mjloop_memory_get` | — |
| Read a report over past runs | `mjloop_report_get` | — |

Nothing else refreshes `INDEX.md`. A story write regenerates its own plan's manifest, so
call `mjloop_index_render` after one if the index is to stay true.

`mjloop_state_get` returns a compact summary rather than the whole file, so the leader's
context does not grow with the cycle count. Read the run directory when you need detail.

`mjloop_verify_run` writes to the run directory and to nothing else: no state, no finding,
no gate, no error signature. It reports an exit code, a headline and a capped list of
failing lines, and it never turns any of them into a verdict — the mapping from an exit
code to `pass`, `fail` or `blocked` is judgement about this project, and it stays with the
agent that has the brief.

`mjloop_report_get` walks past runs and returns one of two projections: `telemetry`, what
every specialist this project drafted actually returned, and `preflight`, the shape of a
run on a track before it starts. Both are reports rather than rules, and neither is folded
into routine output — ask for one when the question is worth the walk.

Memory entries are prose you may correct by hand, but write them with `mjloop_memory_add`:
it allocates the id and names the file. An entry whose frontmatter no longer matches the
schema is skipped by search until it is repaired — it keeps its id either way, so nothing
overwrites it in the meantime.

## Reading a halted run

`.mjloop/runs/<run>/HALT.md` carries the reason, the cycles attempted, the open findings,
and the recommended next step. Read it before restarting anything.
