# MjLoop control center — design

## Status and product rule

The web application becomes the local control center for every MjLoop capability
that the engine can safely expose. It is no longer only a monitor.

The first release supports several linked projects and may run work in different
projects concurrently. A project still has exactly one active MjLoop session.
`.mjloop/state.json` is a single-run record, so two sessions in one project would
race and corrupt the meaning of that record.

The control center does not manufacture capabilities. Claude Code is the only
interactive platform adapter implemented today. Codex and Gemini may be shown by
diagnostics, but remain unavailable until their adapters, installation receipts,
MCP integration, continuation behavior, and protected-write controls exist.

## Existing behavior that remains authoritative

- One project queue is sequential.
- Starting work composes a logical MjLoop command and enqueues it.
- Plan approval, story requeue, and authoritative halt are the only direct
  engine writes currently exposed to the browser.
- `runStart`, `rosterSet`, `runLog`, and `cycleAdvance` never become browser
  writes. They are evidence-producing operations and a click cannot prove work.
- The server remains loopback-only and token protected.
- Terminal transcripts remain bounded.
- Arabic/RTL support and the retained-DOM rendering discipline remain in force.

## Options considered

### 1. Patch the current single-project cockpit

Improve tabs, repair Plans, and add a config form without changing the server
shape. This is the smallest change, but it cannot satisfy linked projects,
parallel cross-project sessions, or a multi-terminal workspace.

### 2. A local hub supervising one runtime per project — selected

Keep the engine state project-local. Add a user-local project registry and a hub
process that owns one `ProjectRuntime` per linked project. Each runtime retains a
sequential queue and one active session; runtimes for different projects may be
active together. This satisfies the first release without changing the engine's
single-run contract.

### 3. Make the engine multi-run inside one project

Give every run independent state, locks, worktrees, and evidence ownership. This
could eventually enable concurrent work in one repository, but it is an engine
migration rather than a web redesign. It is explicitly deferred.

## Delivery slices

### Slice A — current cockpit reliability and safe project config

This slice can ship against the current single-project server.

1. Make the active top-level view unmistakable. Tabs gain a stronger selected
   treatment, a visible page heading and short purpose text. `Run` becomes
   “Current run” in prose while its stable route remains `#run`.
2. Repair the Plans interaction. The current detail is rendered after the whole
   plan list; on a plan with many stories, pressing Open changes state below the
   viewport and appears to do nothing. Opening a plan must expose its detail in
   the user's current context, move focus to its heading, and publish
   `aria-expanded`/`aria-controls`.
3. Turn Config into an editor for the current project. The form covers:
   autonomous mode, limits, verify commands and policy, gates, specialists, and
   track definitions. Advanced raw YAML remains a reader, not an editor.

### Slice B — linked projects and project runtimes

The hub stores a registry outside every repository. A registry entry contains:

```ts
interface LinkedProject {
  id: string
  path: string
  name: string
  linkedAt: string
  lastOpenedAt: string | null
}
```

`id` is generated by the hub and paths are canonical `realpath` values. Linking
validates that the directory exists and reports whether `.mjloop/config.yaml`
is present. An uninitialized project may be linked and offers the supported
`init` workflow; it is not silently initialized.

The registry uses a user-local application directory, a lock, compare-and-swap
revision, backup, temporary file, and atomic rename. It stores no credentials.

The server owns:

```ts
interface ProjectRuntime {
  project: LinkedProject
  queue: JobQueue
  snapshot: SnapshotCache
  clients: Set<Client>
}
```

There is never more than one `JobQueue` per project id. Different runtimes may
pump simultaneously. A global control can stop all sessions during server
shutdown, but it does not merge project state or queues.

HTTP routes become project-scoped:

```text
GET /api/projects
GET /api/projects/:projectId/state
GET /api/projects/:projectId/config
GET /api/projects/:projectId/plans/:planId
...
```

The WebSocket envelope adds `projectId` to snapshots, terminal output,
transcripts, jobs, writes, and receipts. Identifiers, not paths, cross action
messages.

### Slice C — session workspace and terminal layout

The workspace manages terminal panels keyed by
`projectId/platformId/jobId`. A panel shows:

- project and platform;
- queued, launching, running, stalled, stopping, done, failed, or unavailable;
- live terminal or retained transcript;
- Stop, authoritative Halt, Continue/Nudge, Attach, Cancel, and queue controls
  when those actions are valid.

Layouts:

- focused panel;
- one primary panel with two smaller panels;
- equal grid;
- collapsed tray for the rest.

Panels can be promoted, reordered, resized, collapsed, and restored. Layout
preferences are client-only and persisted in local storage; engine facts are
never stored there. Every xterm instance owns its own `ResizeObserver` and sends
resize messages only for its project and job.

The first implementation creates independent terminal panels for independent
project sessions. It does not claim a terminal for each subagent inside a
Claude Code run. Those agents are currently visible only through roster and
result files. Per-subagent terminals require provider streams or engine-owned
child sessions and a new protocol.

### Slice D — platform and agent management

The platform screen reads a versioned adapter registry. Each adapter reports:

- installed and detected version;
- implemented capabilities;
- missing requirements and doctor findings;
- whether interactive sessions, headless agents, continuation, MCP,
  protected-write interception, and per-agent policy are native, emulated, or
  unsupported.

Project settings select an allowed platform set and a default platform. A job
records its chosen platform. The adapter compiles a logical MjLoop command to
host-specific invocation; users do not type host syntax into the queue.

Claude Code remains the reference adapter. Codex and Gemini controls are
disabled until the migration tasks that implement their adapters pass the
compatibility gates in
`docs/superpowers/plans/2026-07-29-mjloop-multi-platform-migration.md`.
Detecting a binary alone is not enough to mark an adapter usable.

Agent management exposes the engine's current track roster and specialist
modes. It may configure supported agent policy but cannot invent live status.
Live agent state remains:

- selected: roster entry exists;
- landed: result file exists;
- completed result: parsed agent result;
- no independent terminal unless the adapter provides one.

## Safe config editing

The existing `writeConfig` rewrites the parsed object, drops comments and
legacy keys, and takes no lock. The browser must not call it.

Add a dedicated config mutation operation:

```ts
interface ConfigPatch {
  revision: string
  changes: Array<
    | { op: 'set'; path: ConfigPath; value: unknown }
    | { op: 'remove'; path: ConfigPath }
  >
}
```

`ConfigPath` is a closed schema, not an arbitrary JSON/YAML path. The operation:

1. acquires the project lock;
2. reads the current raw YAML;
3. refuses a stale revision;
4. parses a YAML `Document` so comments and ordering survive;
5. applies only allowlisted paths;
6. validates the whole result with `ConfigSchema`;
7. writes a backup and temporary file;
8. atomically renames it into place;
9. re-reads and validates the stored file before returning success.

An active run pins its verify policy and track data at start. The editor explains
that changes affect the next run. Fields that would contradict required,
closing, map, or gate agents are rejected by the existing schema and shown next
to the relevant control.

The browser receives localized error codes and structured field paths, never
server-authored prose or stack traces.

## Run and Plans interaction details

Top-level navigation remains URL-addressable. The selected route sets both
`aria-current="page"` and a high-contrast selected surface. Each panel begins
with a visible `h1`, status summary, and primary action where one exists.

Plans uses master-detail behavior:

- desktop: list and detail columns;
- narrow screens: detail replaces the list with an explicit Back action;
- opening a plan updates `aria-expanded`, reveals the detail, scrolls it into
  view without animation when reduced motion is requested, and focuses the
  detail heading;
- the URL may carry the open plan id so refresh/back preserves context.

This fixes the observed failure mode rather than adding a second click handler
to navigation that already works.

## Permissions and command safety

The control center distinguishes:

- read actions;
- reversible conditional writes;
- lifecycle actions with confirmation;
- logical MjLoop commands accepted from a closed command catalog.

The unrestricted free-command bar remains an advanced local control and is
visually separated from standard actions. Multi-project and multi-platform
messages never accept a shell command, executable path, or arbitrary working
directory from the browser. The server resolves those from the linked project
and adapter registries.

## Failure handling

- A stale project or config revision is refused and refreshed.
- A missing linked directory marks the project unavailable; it is not removed.
- An adapter doctor failure disables starting new jobs but leaves history and
  config readable.
- Failure in one `ProjectRuntime` does not stop other projects.
- A failed job blocks only that project's queue.
- Server shutdown stops every runtime using the existing graceful shutdown
  ladder and then closes sockets.
- An unreadable registry falls back to its backup and displays a recovery
  warning. It is never silently reset.

## Tests and release gates

Slice A:

- failing interaction test reproduces Open changing content below the viewport;
- route and active-state tests cover pointer, keyboard, back, forward, and RTL;
- config patch tests cover comment preservation, schema errors, stale revision,
  concurrent writers, backup, atomic failure, and forbidden paths;
- all existing web boundary tests remain green.

Slice B:

- registry traversal, symlink, missing directory, duplicate canonical path,
  stale revision, backup, and recovery tests;
- two projects may run together;
- two jobs in one project remain sequential;
- a failure blocks only its own project;
- shutdown closes all runtimes.

Slice C:

- panel identity survives snapshots and reordering;
- each terminal routes input and resize only to its own job;
- focused, primary-plus-two, grid, and collapsed layouts work at desktop and
  narrow widths;
- keyboard reordering and accessible names accompany pointer resizing.

Slice D:

- unavailable adapters cannot enqueue;
- platform selection is recorded on jobs;
- logical commands compile through the selected adapter;
- Codex/Gemini remain unavailable until their capability and compatibility
  suites pass.

Every slice runs web tests, config/schema tests, typecheck, build, Arabic/English
locale exhaustiveness, and the existing shipment verification appropriate to
the changed boundary.

## Deferred capabilities

- concurrent sessions in one project;
- automatic worktree isolation for parallel runs;
- independent terminals for provider-managed subagents;
- direct provider HTTP API calls;
- browser-managed credentials;
- marking Codex or Gemini usable before their adapters pass compatibility.
