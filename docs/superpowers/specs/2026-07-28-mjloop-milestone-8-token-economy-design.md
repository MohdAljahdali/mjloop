# mjloop — Milestone 8: Derived Working Memory — Design

**Status:** approved, ready for planning
**Extends** `2026-07-27-loop-milestone-5-guards-design.md` (the guards),
`2026-07-27-loop-milestone-7-memory-and-extension-design.md` (the store), and
`2026-07-28-mjloop-cockpit-design.md` (the read surface and the write boundary).

## 1. Problem

A run regenerates its own narrative every cycle.

Cycle 3 opens with a brief the leader retypes, a codebase the builder re-reads, a
test suite the verifier re-runs, and a list of findings the leader re-sorts. All
four already happened in cycle 2, and the engine watched all four happen. What it
kept was `state.findings`, `state.cycle_errors`, and a directory of per-agent JSON
that nothing reads back.

The cost lands in three places, and they compound.

**The engine cannot see what it is judging.** `verify.test`, `verify.lint` and
`verify.build` have existed since milestone 1 (`schemas/config.ts:67-71`) and **no
engine code has ever read them**. They are a hint the leader types into the
`Verify:` line of a brief, which the verifier model then runs with `Bash` and
summarises by hand into `evidence[].excerpt`. The engine records the excerpt
verbatim. It cannot tell a suite that exited 0 from a paragraph describing one.
`ops/log.ts:149-153` says so in as many words: *"the engine cannot read an excerpt
and confirm it shows a failure."*

**Nothing is bounded.** `EvidenceSchema.excerpt` is `z.string()` with no ceiling
(`schemas/contract.ts:29`). Whatever an agent pastes lands verbatim in
`cycle-NN/verifier.json`, and if that agent proves a gated track's gate, in
`state.reproduction.excerpt` and therefore in `state.json` (`ops/log.ts:190-192`),
which is re-read, re-validated and re-written on every subsequent state mutation
for the rest of the run.

**The measured distribution, so the rest of this document can be argued against
numbers rather than adjectives.** Every figure below was taken against this
repository's own configured `verify.test` (`cd engine && npm test`, 781 tests
across 49 files):

| Case | Lines | Bytes |
|---|---|---|
| Green | 13 | 270 |
| One broken function | ~170 | ~8 KB |
| One broken constant taking out 58 tests across 9 files | ~820 | ~44 KB |

So the realistic ceiling is under a thousand lines, the typical failing cycle is
about 8 KB (~2K tokens), and a green cycle is about 90 tokens. An earlier draft of
this document argued from "4,000 lines of jest output"; that number was invented
and it is retired. §2 restates every idea's expected saving against the table
above, because an idea that costs a new file, a new tool and a new schema field
has to be weighed against one that costs a single exported function.

**Every cycle rediscovers the ground.** There is no artefact between cycles. The
leader hands forward `carried_findings` — the raw, unsorted, undeduplicated
`state.findings` array as of the moment the cycle closed (`ops/run.ts:163`) — and
nothing else. A `scout` map produced in cycle 1 exists only as a `summary` string
inside `cycle-01/scout.json`, which no later brief mentions and no later agent
opens.

Underneath all three: **a run owns no derived working memory.** It owns a state
file describing the present instant, and an archive nothing reads. Everything in
between is regenerated from the model's context, every cycle, at full price.

## 2. What this milestone changes

Nine changes, in three groups.

**Derived working memory** — the run starts keeping what it learned.

1. `mjloop_verify_run` — the engine runs the configured verify command itself,
   writes the full output to `cycle-NN/verify/<slot>.log`, and returns a bounded
   digest. The verifier judges the digest.
4. `map.md` — a run-scoped map written once from the mapping agent's own result,
   carried into every later brief by a `Map:` line.
5. `handoff.md` — a deterministic per-cycle summary generated by
   `mjloop_cycle_advance` from what the cycle already knows. No extra model call.

**Engine-boundary hardening** — the ceilings the schemas never had.

2. `Evidence.excerpt` is capped at 2,000 characters, with the remainder spilled to
   a file the marker names. Lossless.
3. A verify-result cache keyed on a git worktree digest, scoped to one run, and
   populated only by results that exited 0.
6. `carried_findings` is deduplicated on the identity `cycleFingerprint` already
   defines.

**What the operator sees, and when work happens.**

7. Specialist hit-rate telemetry, aggregated from rosters and agent results across
   runs.
8. A preflight estimate before the first dispatch, derived from comparable runs.
9. `docs` becomes a run-closing agent rather than a per-cycle one.

### The ledger

A milestone whose stated purpose is cutting context must be able to say what each
idea costs and what it returns. Measured against a representative 3-cycle `build`
run on this repository — two failing cycles, a four-agent roster — using §1's
table:

| Idea | Per-run context change | Implementation cost |
|---|---|---|
| 1 — `mjloop_verify_run` | **−16 KB to −78 KB** on failing cycles; ~0 on green | one file, one MCP tool, two config fields, one run-directory pin, one reuse of the existing lock |
| 6 — deduplicate findings | **−4 KB to −16 KB**, unconditional | one exported function, two call sites |
| 9 — `docs` closes the run | **−20 KB to −60 KB**, but only on a run that would otherwise have drafted `docs` twice; 0 otherwise | one track field, one `runLog` branch |
| 4 — `map.md` | **−5 KB to −20 KB** once bounded (§7's cap); it was *positive* under the uncapped append rule | one track field, one writer |
| 5 — `handoff.md` | **−2 KB to −8 KB** once §8's cap lands *and* the brief drops the two lines the handoff now owns; it was **+8 KB to +32 KB** as first drafted | one writer, one brief change |
| 2 — cap `Evidence.excerpt` | **~0 model tokens.** It bounds `state.json` re-validation and the cockpit payload, which are disk and network | one constant, one pure function |
| 3 — verify cache | **0 tokens** by design, and 0 by default. Its return is **wall clock** — 1.8 s per skipped suite on this repo | one file, three git invocations, ~15 tests |
| 8 — preflight | **0** under its `auto` default. When set to `human`, ~1 KB once per run, and the saving is whatever the operator then trims | one file, one config key |
| 7 — telemetry | **0** once §10 keeps the full table out of routine output; one line in `/mjloop:status` | two files, one route |
| the MCP surface itself | **+~250 tokens permanently**, in every context this server is attached to | two new tools (16 → 18) |

Three consequences, and they changed this design rather than being noted beside
it:

- **Idea 6 ships first**, in batch 1. It is the only addition-free cut in the
  milestone: no new file, no new tool, no new schema field, no new disk artefact.
  It is also the test every other idea is now held to — *does it add a file, a
  tool, a schema field, or an unbounded artefact, and is there a measured number
  defending that cost?*
- **Every artefact this milestone introduces carries a stated, enforced ceiling.**
  `map.md` (§7), `handoff.md` (§8), `VerifyDigest.failures` and `headline` (§4),
  the excerpt and now `claim` and `ref` (§5), the telemetry table (§10) and the
  history walk (§10). An unbounded artefact in a token-economy milestone is a
  defect, not an omission.
- **Ideas 5 and 7 were the two the first draft argued for most confidently and
  the two that added the most context.** Neither is deferred, because both fix
  real defects; both are re-scoped until the column above is negative or zero.

Idea 1's two safety mechanisms — the pinned verify block and the project verify
lock (§4) — are held to the same standard and pass it. The pin is a file the model
never reads; the lock is a directory nobody serialises into a context. Together
they add two fields to a digest an agent was already receiving and one phase value
to a ledger entry, which is single-digit tokens per invocation, and they are why
the row above can be believed at all: a measured saving on a command an agent
could have rewritten a moment ago is not a measurement.

## 3. Non-goals

- **The engine does not judge.** This is the milestone's hardest line and §4 is
  written around it. `mjloop_verify_run` executes and reports; it never sets a
  status, never writes `state.json`, never calls `runLog`, and never opens a gate.
  A verifying agent still returns the verdict, and the verdict is still only as
  good as the evidence attached to it.
- **No price table, no token counts.** Idea 8 estimates in cycles, agent
  dispatches and minutes — units the engine can observe. §11 explains why a
  currency figure would be a guess wearing an estimate's clothes.
- **No cross-run verify cache.** §6 confines the cache to one run, for reasons
  that are about environments rather than about hashing.
- **No new writer of `state.json`.** The MCP server owns it. Every artefact this
  milestone adds is a file beside the state, not a field inside it, except two
  nullable timestamps that `runStart` and `cycleAdvance` already had the lock for.
- **No config migration.** `loadConfig` strips legacy keys and adds nothing — the
  strip itself is at `store/config-store.ts:34-41`; `schemas/config.ts:74-90` is
  the doc comment explaining it. Every new key below carries `.default(...)`, so an
  existing `.mjloop/config.yaml` keeps parsing and gains the new behaviour's safe
  setting without being touched. Where the *default value* changes behaviour —
  idea 9 — §12 says exactly what an existing project does and does not get.

## 4. Idea 1 — `mjloop_verify_run`

### What exists today

`.mjloop/config.yaml` holds three shell strings:

```yaml
verify:
  test: cd engine && npm test
  lint: cd engine && npm run typecheck
  build: cd engine && npm run build
```

`VerifySchema` (`schemas/config.ts:67-71`) validates them. `ops/init.ts:38-53`
detects them from `package.json`. `readConfigView` (`web/read.ts:60`) shows them.
**Nothing runs them.** The leader copies them into the brief's `Verify:` line
(`skills/mjloop-contract/SKILL.md:21`), the verifier is told that line is
authoritative (`agents/verifier.md:18-22`), runs the commands with `Bash`, and
writes what it saw into `evidence[].excerpt`.

`runLog` then accepts that excerpt without inspection. It checks the agent's name
against the track, checks the gate, and derives error signatures from the
excerpt's first line (`ops/fingerprint.ts:82-97`). It has no way to know whether
the command ran.

There is no command runner anywhere under `engine/src` outside `src/web/`
(`web/cli.ts:2`, `web/session.ts:82`), and `node:child_process` is a builtin, so
this adds no dependency.

### The change

**New file — `engine/src/ops/verify.ts`.**

```ts
export type VerifySlot = 'test' | 'lint' | 'build'

export interface VerifyRunInput {
  slot: VerifySlot
  /** Distinguishes two runs of one slot in a cycle. Validated by AgentNameSchema. */
  label?: string
  /** How long to wait for the child before returning `phase: 'running'`. */
  wait_ms?: number
}

export interface VerifyFailure {
  /** One decisive line, trimmed, never longer than 240 characters. */
  line: string
  /** Where in the log it came from, so the reader can jump to it. */
  at: number
}

export interface VerifyDigest {
  /** `'queued'` means **nothing ran**: another verify command in this project
   *  holds the lock. See "The project verify lock". */
  phase: 'complete' | 'running' | 'queued'
  slot: VerifySlot
  /** What was executed — from the run's **pinned** copy, never from the live
   *  `config.yaml`. See "What the engine executes". */
  command: string
  /** Which copy of the verify block this invocation executed. `'live'` occurs
   *  only for a run started before this milestone. */
  source: 'pinned' | 'live'
  /** What `.mjloop/config.yaml` holds for this slot *now*, when it differs
   *  from the command that ran. `null` when they agree, and when there is no
   *  pin. A mid-run edit is made visible without being obeyed. */
  live_command: string | null
  /** Repo-relative: `.mjloop/runs/<run>/cycle-NN/verify/<name>.log`. Empty
   *  while `phase === 'queued'` and for a null slot — nothing was written. */
  log: string
  /** `null` while `phase` is `'running'` or `'queued'`, and on a timeout or a
   *  kill. */
  exit_code: number | null
  timed_out: boolean
  /** True when this digest was reused from an earlier cycle. See §6. */
  cached: boolean
  cached_from_cycle: number | null
  /** The decisive line. See "What a digest extracts". Max 240 chars. */
  headline: string
  /** At most FAILURES_MAX (20) entries. */
  failures: VerifyFailure[]
  /** How many decisive lines were found, so the 20-entry cap is visible. */
  failures_total: number
  lines: number
  bytes: number
  duration_ms: number
  /** The cache fingerprint (§6). `null` when the cache is off or the worktree
   *  could not be digested. It is NOT the in-flight de-duplication key. */
  fingerprint: string | null
}

export async function verifyRun(
  projectDir: string,
  input: VerifyRunInput,
  now?: Clock,
  /**
   * Stops the *wait*, never the child. See "The request signal" below.
   * Named `waitSignal` so the distinction survives the implementer.
   */
  waitSignal?: AbortSignal,
): Promise<VerifyDigest>
```

**Preconditions**, in this order, matching `rosterSet` and `runLog`:

1. `new StateStore(projectDir).get()`. `status === 'running' && track !== null`
   writes into `cycle-NN/verify/`. `status === 'done' && track !== null` is also
   accepted and writes into `closing/verify/` — this is the concession §12
   requires so a closing agent can re-run the suite against the code as it
   finally stands, and so the commit that ships the run can rest on a green
   digest taken *after* the documentation landed. **This widening is deliberate
   and operator-confirmed** (§16): it is the one precondition in this milestone
   that admits a terminal state, and it is admitted because the alternative is a
   run whose last verified tree is not the tree it ships. It buys nothing for an
   attacker — the closing path writes outside every cycle directory, files no
   findings and touches no state (§12) — and it is bounded by `track !== null`,
   so a project with no run at all is still `NoActiveRunError` (`ops/run.ts:19`),
   as is every other status.
2. The verify block comes from the run's **pinned copy**, not from
   `loadConfig(projectDir)` — see "What the engine executes" below. A `null` slot
   is **absent by design**, which `agents/verifier.md:27-30` already encodes as a
   rule the verifier follows. `verifyRun` returns `phase: 'complete'`,
   `exit_code: null`, `headline: 'slot is null in config — nothing to run'`, and
   writes no log. It is not an error, because a project with no build step has
   not made a mistake.
3. The log name is `slot` or `` `${slot}--${label}` ``, and `label` goes through
   `AgentNameSchema` (`schemas/contract.ts:16`). That schema is the only
   path-traversal defence in this system, and a name that reaches the filesystem
   goes through one check in one place (`ops/log.ts:161-162` says exactly this).

### What the engine executes — the run's pinned verify block

`verifyRun` executes a shell string. Where that string comes from *is* the trust
boundary, so it is fixed here rather than left to whatever `loadConfig` returns at
the moment of the call.

**The invariant: what the engine executes during a run is decided once, at run
start, and nothing the run itself writes can change it.**

**Where the pin lives.** `runStart` already creates the run directory as its last
act (`ops/run.ts:100`). It now writes one more file there —
`.mjloop/runs/<run>/verify-pinned.json`:

```json
{
  "version": 1,
  "pinned_at": "2026-07-28T10:31:00.000Z",
  "verify": {
    "test": "cd engine && npm test",
    "lint": "cd engine && npm run typecheck",
    "build": "cd engine && npm run build",
    "timeout_ms": 900000,
    "lock_timeout_ms": 1800000,
    "failure_patterns": { "test": [], "lint": [], "build": [] }
  }
}
```

**Its schema is `VerifySchema` itself, wrapped:**

```ts
export const PinnedVerifySchema = z.strictObject({
  /** Bumped only if this wrapper's own shape changes. The block inside it needs
   *  no version of its own: it is re-parsed through the live `VerifySchema`, so
   *  a pin written before a key existed gains that key's default on read. */
  version: z.literal(1),
  pinned_at: z.string(),
  verify: VerifySchema,
})
```

Reusing `VerifySchema` rather than restating the three strings is what makes the
pin survive this milestone's own successors: every future `verify.*` key is
pinned automatically, and every pin written before it existed keeps parsing. It
lands in `engine/src/schemas/verify.ts` beside `LedgerEntrySchema` (batch 1),
because `runStart` (2b) writes it and `verifyRun` (2a) reads it, and neither may
depend on a module its batch-mate is still writing (§15).

**The whole block is pinned, not only the three commands.** `timeout_ms` and
`failure_patterns` are executed policy too: a `timeout_ms` rewritten to `1` kills
every suite the engine starts, and a failure pattern is a regular expression this
engine compiles and runs. Pinning the object is also the simpler invariant to
state and the smaller thing to test. `verify_cache` is deliberately **not**
pinned: it is top-level, it decides whether a proven-green result may be reused
rather than what runs, and §6 already confines the cache to one run.

**Why a file, and not a field on `state.json`.** Because a file can be protected
by basename. `PROTECTED_BASENAMES` becomes
`['state.json', 'manifest.json', 'verify-pinned.json']` (`store/paths.ts:31`),
and `evaluateStateGuard` matches the basename of any path under `.mjloop/`
(`cli/index.ts:89-101`) — so one word covers every run directory of every project,
with no change to the guard, the hook, or `hooks/hooks.json`. Putting it in
`state.json` would instead have widened the one document the MCP server owns, for
a value that never changes after it is written.

**Written once, and structurally so.** The write uses `flag: 'wx'` and treats
`EEXIST` as success rather than as an error. `/mjloop:resume` continues an
existing run rather than calling `runStart`, so ordinarily nothing attempts a
second pin; `wx` is what makes "ordinarily" something nobody has to reason about.
A resumed run therefore executes what it started with, which is the whole point —
a resume that re-pinned would reopen the hole for anyone willing to wait for an
interruption.

**When there is no pin.** Two absences, and conflating them is what would make
the pin decorative:

| State | What it means | What `verifyRun` does |
|---|---|---|
| `state.started_at === null` | A run started before this milestone — §11 makes `runStart` the only writer of `started_at` | Falls back to `loadConfig`, and says so: `source: 'live'` |
| `started_at !== null`, pin absent | The pin was written at run start and then removed | `PinnedVerifyMissingError`, naming the file |
| Pin present, will not parse | A partial write, or tampering | `PinnedVerifyInvalidError`, naming the file |

The asymmetry is deliberate: **absent-and-old is legacy; absent-and-new is a
deletion.** Falling back to the live config on a missing or broken pin would make
`rm` the downgrade attack the pin exists to prevent — and the `PreToolUse` hook
matches `Write|Edit` (`hooks/hooks.json`), not `rm` through `Bash`. `started_at`
is what closes that gap without a new field: this milestone adds it in the same
batch, so every run that *could* carry a pin does, and its absence is decidable
rather than guessable. The residual is stated rather than argued away — an agent
can still delete the file, and what it earns for that is a run that refuses to
verify at all.

**When the pin and the live config disagree.** The pinned command runs. The live
one is reported and never obeyed: the digest carries `live_command` and so does
the ledger entry, so the drift is durable, reaches `handoff.md`'s verification
table (§8), and appears beside the cycle's verify rows in the cockpit (§13)
without a new route or a new reader. **Drift refuses nothing.** A rule that
halted a run on drift would hand any agent holding `Write` a way to stop the run
by editing a file this design deliberately leaves hand-editable.

**Hand-editability is preserved, exactly as milestone 7 decided.** `config.yaml`
remains a file a person edits and `/mjloop:add track` keeps writing it
(`2026-07-27-loop-milestone-7-memory-and-extension-design.md` §5). An edit to
`verify:` takes effect at the next `runStart`, which is where an operator already
expects a change to a run's configuration to land, and which is the only claim
about timing this design has to make.

### What a digest extracts

This is the part the whole idea rests on, and the first draft left both fields
undefined. Measured on this repository, the first non-empty line of
`cd engine && npm test` is `> @mjloop/engine@0.4.1 test` and the first non-empty
line of `cd engine && npm run typecheck` is `> @mjloop/engine@0.4.1 typecheck`.
Those are npm's script echo. They are identical on green and on red, they carry
no information, and — because `errorSignature` hashes the *first line* of an
excerpt (`ops/fingerprint.ts:95-97`) — defining `headline` as "the first non-empty
line" would give every failure of a command one constant signature, `errorFingerprint`
would match on the second consecutive failing cycle, and `cycleAdvance`
(`ops/run.ts:185-196`) would halt a run that was making progress with *"the same
verification failure recurred"*. A banner must never become a signature.

So both fields are specified, and both are pinned by tests over **real captured
output** rather than synthetic strings:

**Skip list.** Lines matching `^>\s` (npm's script echo) and the runner's own
banner (`^\s*RUN\s+v[\d.]`) are never candidates for `headline` or `failures[]`.
They stay in the log, which is complete; they are excluded from the digest, which
is a summary.

**`failures[]`** is every line matching the slot's failure pattern, in file order,
capped at `FAILURES_MAX = 20`, with `failures_total` reporting how many were found.
The default pattern list is one exported constant per slot in `ops/verify.ts`:

```ts
/** Documented defaults. `verify.failure_patterns.<slot>` overrides them. */
export const FAILURE_PATTERNS: Record<VerifySlot, RegExp[]> = {
  test:  [/^\s*(FAIL|×|✗|✕)\s/, /^\s*\d+\)\s/, /\bAssertionError\b/, /^\s*Error:\s/],
  lint:  [/^[^\s].*\(\d+,\d+\):\s+error\s+TS\d+/, /^\s*error\s/i],
  build: [/^\s*(error|ERROR)\b/, /\bfailed\b/i],
}
```

`verify.failure_patterns` is an optional per-slot array of strings in
`config.yaml`, compiled with `new RegExp(pattern)` inside a `try` — an invalid
pattern falls back to the default and is reported in the digest's `headline`
rather than thrown, because a typo in a regex must not stop a project verifying.

**`headline`** is, in order of preference:

1. the **last** summary-shaped line before exit — a line matching
   `/^\s*(Tests|Test Files|Snapshots)\s/` or `/\b\d+\s+(failed|passed|errors?)\b/`.
   On this repo that is `Tests  58 failed | 723 passed (781)`, which is the single
   most informative line in a 44 KB log and which line 1 would have missed;
2. otherwise `failures[0].line`, when any failure was found;
3. otherwise the first non-skipped, non-empty line.

Trimmed to 240 characters. Digit runs are left intact in the digest — the
collapsing to `N` happens inside `errorSignature`, and doing it twice would make
the log and the signature disagree about what was seen.

The consequence for the guard is stated as an invariant, not left implicit: **two
different failures of one command must produce two different signatures.** §14
pins where the signature is computed, and `tests/ops/fingerprint.test.ts` gains
the assertion over a captured vitest log.

**Execution.** `spawn(command, { cwd: projectDir, shell: true, stdio: ['ignore',
'pipe', 'pipe'] })`. `shell: true` is mandatory: the config values are shell
strings (`cd engine && npm test`), not argv arrays, so there is no escaping to be
had. `stdio: 'inherit'` is forbidden and must be named as forbidden in the file's
comment — `StdioServerTransport` binds `process.stdout` as the JSON-RPC channel
(`sdk/.../stdio.js:9`), and one inherited byte corrupts the session's protocol
stream irrecoverably. stdout and stderr are interleaved into one log in arrival
order, because a failure's stack and the test name that produced it are usually
on opposite streams and separating them makes the log unreadable.

**Two timeouts, and they answer different questions.**

| | Value | On expiry |
|---|---|---|
| `wait_ms` | input, default 45 000 | Return `phase: 'running'`. The child keeps running. |
| `verify.timeout_ms` | config, default 900 000 | `child.kill('SIGTERM')`, then `SIGKILL` after 5 s. `timed_out: true`, `exit_code: null`. |

The MCP SDK's client-side default request timeout is 60 000 ms
(`sdk/.../protocol.js:8`), the server can only extend it by emitting progress the
caller opted into, and `.claude-plugin/plugin.json` sets no `env`, so
`MCP_TIMEOUT` is whatever the user happens to have. A tool that blocks for a
four-minute test suite therefore dies mid-request and the leader learns nothing.
So `verifyRun` waits `wait_ms` — deliberately under the SDK default, with room
for framing — and if the child has not exited, returns `phase: 'running'` with the
log path, the elapsed time, and the last few lines already on disk.

**The request signal.** `mjloop_verify_run` receives `extra.signal`
(`sdk/.../protocol.d.ts:177`), which fires when the client cancels or times out
the request. It is passed as `waitSignal` and it **stops the wait, never the
child**. A user with `MCP_TIMEOUT=30000` would otherwise have a four-minute suite
killed at 30 s and re-run from zero by the next call — the exact opposite of what
`phase: 'running'` exists to achieve. On abort, `verifyRun` abandons its own
pending wait and leaves the child attached to the module-level completion promise,
so the next call learns the exit code. **Only `verify.timeout_ms` kills a child.**
This is stated in the parameter's name, in its doc comment, and in the file's
header comment, because it is the kind of distinction that does not survive being
implied.

**Two promises, not one.** The de-duplicator holds the **completion** promise —
the one that settles when the child exits. What a caller receives is
`Promise.race([completion, waitTimer])`. Conflating them breaks in both
directions: storing the wait-bounded promise means a slow suite resolves once as
`phase: 'running'` and every later call is handed that same stale digest forever,
so the exit code is never observable and the cache (which requires
`exit_code === 0`) can never be populated for exactly the suites worth caching;
storing only the completion promise means a second caller blocks past the 60 s
client timeout, which is the failure `wait_ms` exists to avoid.

**Calling again attaches; it does not respawn.**

```ts
/** In-flight de-duplication only. Lifetime bounded by the child process. */
const inFlight = new Map<string, Promise<VerifyDigest>>()
const key = `${slot}::${label ?? ''}::${command}`
```

Three properties of that key, each fixing a way the first draft was wrong:

- **It is keyed on `slot`, `label` and `command`, not on the cache fingerprint.**
  Concurrency de-duplication and cache identity are different questions and must
  not share a key. The fingerprint is `string | null` and is computed only when
  `verify_cache` is on (§6), so in a non-git project — or in any project with the
  cache off, which is every project by default — every call would collide on one
  null key and a `lint` call would be handed the in-flight `test` call's digest.
  `slot`, `label` and `command` are always available and never null.
- **It is pruned when the child settles**: `inFlight.set(key, p); void p.finally(() => inFlight.delete(key))`.
  Without the prune, a module-level map in a process that lives for the whole
  session (`plugin.json`) is a permanent memo of every verify result across every
  cycle and every run — an unconditional cache that ignores `verify_cache`,
  memoises **failing** results, survives `runStart`, and never re-checks that the
  log still exists. That is every safety rule §6 establishes, bypassed by an
  optimisation. The map is an in-flight de-duplicator and its lifetime is the
  child's.
- **Its scope is one process, and that is not the scope the hazard has.**
  Within one MCP server process, a second identical call attaches to the first.
  Across processes it cannot: `/mjloop:web` spawns one `claude` per queued job
  (`web/queue.ts:227` → `web/session.ts:82`), each with its own MCP server, so two
  concurrent runs in one project can put two test suites on the same port. A map
  in one process's memory is the wrong instrument for that, and pretending
  otherwise would be a false guarantee about the one thing an operator would rely
  on it for. **Mutual exclusion across processes is a separate mechanism with a
  separate scope — "The project verify lock" below — and the two compose in a
  fixed order rather than one being stretched to cover the other's question.**

**Never inside the *state* lock.** `verifyRun` calls no `StateStore.update`.
`withLock`'s default acquire timeout is 5 000 ms (`store/lock.ts:54`), so a
subprocess held inside `.mjloop/.lock` would starve every other tool in the
session. It reads state once, unlocked, exactly as `rosterSet`
(`ops/roster.ts:24`) and `runLog` (`ops/log.ts:112`) do. The verify lock below is
a **different directory** taken for a different reason, and keeping the two apart
is what lets a fifteen-minute suite run while the leader still logs results.

**The ledger.** Every invocation appends to `cycle-NN/verify/index.json`:

```json
[
  {
    "slot": "test",
    "command": "cd engine && npm test",
    "source": "pinned",
    "live_command": null,
    "log": "test.log",
    "phase": "complete",
    "exit_code": 1,
    "timed_out": false,
    "fingerprint": "9f2c…",
    "cached_from_cycle": null,
    "at": "2026-07-28T10:36:00.000Z"
  }
]
```

The ledger is the milestone's load-bearing artefact: it is the engine's record of
what the engine itself executed, and §5, §6, §8 and §10 all read it. Its zod
schema lives in `engine/src/schemas/verify.ts` and lands in **batch 1**, not in
`ops/verify.ts`, so every downstream consumer typechecks against a settled floor
(§15).

**An entry is amended, not merely appended.** An invocation that has not finished
writes its entry immediately — `phase: "queued"` before the lock is won,
`phase: "running", exit_code: null` once the child is spawned — and when the child
finally exits, `verifyRun` **rewrites that entry in place** with the real `phase`,
`exit_code`, `timed_out` and `duration_ms`. Without the amendment a suite that
ultimately exits 1 leaves a ledger reading `null` forever, and the contradiction
check below — which is the whole reason the ledger exists — is inert against it.
The rewrite is an ordinary read-modify-write of a small JSON array in the cycle
directory, matched on the entry's `at` and log name; it takes no lock, because
`verifyRun` is the only writer of that file.

A digest with `phase: 'running'` or `phase: 'queued'` is **not yet evidence**.
`agents/verifier.md` gains that in as many words: neither is a `pass` — each is a
`blocked` or a reason to call again.

### The project verify lock

The in-flight de-duplicator is a map in one process's memory, and the hazard is
not scoped to one process. `/mjloop:web` spawns one `claude` per queued job, each
with its own MCP server; two of them in one project can run two test suites at
once, on one port, against one database, in one working tree. Neither suite is
wrong and both go red. That failure is worse than slow: a red digest arms
`errorSignature`, and two cycles colliding the same way arm `errorFingerprint`,
so `cycleAdvance` (`ops/run.ts:185-196`) can halt a run with *"the same
verification failure recurred"* over a port nobody was fighting for.

**The mechanism already exists and is not changed.** `store/lock.ts` is 166 lines
of `mkdir`-based, cross-process mutual exclusion with stale reclaim, an identity
check on release, and a serialised reclaim path — all of it argued out in
comments that took real races to write. `verifyRun` reuses `withLock` **as it
stands**: no new lock primitive, no edit to `store/lock.ts`, no second
implementation of a thing this repository already got right. What the design
supplies is a different lock directory and different options.

**What it is keyed on: the project, not the slot.** The new path is
`resolveLoopPaths(projectDir).verifyLock` — `.mjloop/.verify-lock`, beside the
state lock and never the same directory as it.

Keying per slot would be finer and would be wrong. The contended resource is not
the slot; it is the machine — a port, a fixture database, a build output
directory, a temp path — and **the engine cannot know which two commands share
one.** A project whose `build` starts a preview server on the port its `test`
suite binds would serialise perfectly per slot and collide anyway, which is the
worst kind of guarantee: one that reports success. Serialising the whole project's
verify execution costs wall clock in the one case where two slots were genuinely
independent, and that case is a wait; the alternative is a false red, and a false
red is what halts runs.

Two consequences are stated rather than discovered. `test` and `lint` dispatched
in the same cycle now run one after the other, in one process as well as across
several — `withLock` is not reentrant and this design does not make it so, because
same-process concurrency binds the same port as cross-process concurrency does.
And the scope is the `.mjloop/` directory: **two clones of one repository on one
machine still share a port and cannot see each other's lock.** That is a limit of
where the lock file lives, said plainly rather than claimed away.

**The three options, and why each is what it is.**

| Option | Value | Why |
|---|---|---|
| `timeoutMs` | `verify.lock_timeout_ms`, default 1 800 000 | Two full ceilings. A waiter must never give up on a suite that is still legitimately running, and one holder can legitimately hold for `timeout_ms`. |
| `staleMs` | `verify.timeout_ms + VERIFY_LOCK_STALE_MARGIN_MS` (60 000), derived, never configured | **The invariant: the staleness threshold is always strictly greater than the longest a live holder can hold.** `withLock` ages a lock from its `mtime` and nothing refreshes it, so a threshold below the ceiling would reclaim the lock out from under a running suite and produce exactly the two-suites-on-one-port state the lock exists to prevent. Deriving it from `timeout_ms` means the two cannot be configured into contradiction. |
| `pollMs` | 250 | A verify wait is measured in minutes. The 25 ms default is 72 000 wakeups over half an hour to answer a question that changes at most once. |

**A killed holder costs a bounded wait, not a hang.** A `claude` process killed
mid-suite leaves the directory behind; `withLock`'s reclaim removes it once it
ages past `staleMs`, and until then every call returns `phase: 'queued'` rather
than blocking. The worst case is therefore the ceiling the operator already
configured plus a minute — and `verify.timeout_ms` is the number they set to
answer exactly the question "how long may a command of mine run".

**What a waiter is told: `phase: 'queued'`, and the truth.** A call that cannot
take the lock within `wait_ms` returns a digest with `phase: 'queued'`,
`exit_code: null`, `log: ''` — nothing has been written — and
`headline: 'another verify command is running in this project — call again'`.
It does **not** return `phase: 'running'`, because no child of this call is
running and a digest that says otherwise is the one lie this whole design is
built to avoid. The wait continues in the background: the lock is still being
waited on, and the next call attaches to it (below) or finds the finished result.
If the acquire finally times out after `lock_timeout_ms`, the wait resolves to a
terminal `queued` digest whose headline names the give-up; it never rejects into a
promise nobody is awaiting.

**A queued invocation writes a ledger entry.** `phase: "queued"`, amended in place
to `"running"` when the lock is won and to `"complete"` when the child exits — the
same amendment mechanism, matched on the same `at` and log name, which are both
known before the file exists. Without the entry, a verifier could log
`status: "pass"` citing a command that only ever queued and the contradiction
check would have nothing to read. So `LedgerEntrySchema.phase` is a three-member
union and the check's refusal list (below) names `queued` beside `running`.

**How it composes with the de-duplicator — the order is load-bearing.**

1. `inFlight.get(key)` first. A second call in the same process for the same
   `slot::label::command` attaches to the first and takes no lock. Reversing these
   two steps would queue a process behind a lock it already holds — `withLock` is
   not reentrant, so that is a self-inflicted `lock_timeout_ms` stall for an answer
   already in flight three lines away.
2. On a miss, the completion promise is created and registered, and everything
   below happens *inside* it: the cache lookup (§6) — **a cache hit takes no lock
   at all**, because it executes nothing and needs exclusion from nothing — then
   `withLock(paths.verifyLock, …)`, then the pre-spawn digest, the child, the
   post-exit digest, and the cache decision, and only then release. §6's equality
   check compares two digests taken around the child; taking them outside the lock
   would compare against a tree another process is already moving.
3. The caller still receives `Promise.race([completion, waitTimer])`. The in-flight
   entry carries whether the child has spawned, so the wait branch can tell the two
   waits apart: spawned means `phase: 'running'`, not yet means `phase: 'queued'`.
   One field, and it is the difference between two honest answers.

So the map answers *"is this same command already in flight here?"* and the lock
answers *"is any verify command executing in this project?"* — two questions, two
mechanisms, and neither is asked to answer the other's.

### How this strengthens the evidence rule

The objection to writing this tool is obvious and must be answered: *does moving
execution into the engine let the engine declare a pass?*

No — with one honest qualification the first draft did not state, and which is
answered in prose because the engine cannot answer it in code.

**The qualification: nothing stops the leader calling the tool.**
`mjloop_verify_run` is an ordinary MCP tool and the leader holds the MCP surface.
Today, a leader that wanted to log a `verifier` result it authored itself had to
invent plausible command output, and that friction is what the evidence rule has
actually rested on — `ops/log.ts:149-153` concedes the engine cannot read an
excerpt. After this change the leader could call the tool, receive an authentic
engine-produced green digest, transcribe it into a contract-valid `verifier`
result, and log it; the contradiction check below only ever refuses, so it is
inert against a green ledger. The rebuttal "the only way to reach
`mjloop_run_log` is for an agent to return a contract-valid result" is a statement
about *shape*, and the engine cannot distinguish a result an agent returned from
one the leader typed.

The engine cannot see caller identity, so the rule goes where it is enforceable —
in the leader's own instructions, which is where "Never declare success on your
own reading of the code" already lives (`skills/mjloop-leader/SKILL.md`, step 5).
`skills/mjloop-leader/SKILL.md` gains, in **What you never do**:

> **Never call `mjloop_verify_run` yourself.** The verifying agent obtains its own
> digest. A digest you fetched is not that agent's evidence, and pasting one into
> a brief makes you the verifier.

and `agents/verifier.md` gains the matching half: the verifier calls the tool
itself and must not accept a digest handed to it in its brief. This is named as a
prose control, not dressed up as a structural one.

With that stated, the design makes engine-declared success structurally
impossible in four ways.

**`verifyRun` returns facts, not a verdict.** There is no `status` field on
`VerifyDigest`, and `phase` is deliberately not called `status` so the two words
never sit beside each other in a leader's context. Exit 127 is `exit_code: 127`,
not `blocked`. Exit 1 is `exit_code: 1`, not `fail`. The mapping from an exit code
to a verdict is judgement about *this* project — `agents/verifier.md:26-37`
carries four paragraphs of it — and it stays with the agent that has the brief.

**`verifyRun` writes no state.** It never touches `state.json`, never files a
finding, never appends an error signature, never probes the gate. The only path
from a command's output into the run's state is still `mjloop_run_log`, and the
only way to reach `mjloop_run_log` is still for an agent to return a contract-valid
result naming a status it chose.

**It closes a hole the evidence rule has always had.** Today a verifier can log
`status: "pass"` with an `evidence` entry whose `ref` is `npm test` and whose
`excerpt` is `"tests 40, pass 40, fail 0"` **without having run anything**. The
engine has no counter-evidence. With a ledger it does, so `runLog` gains one
check:

> **Contradicted evidence.** When a result carries `status: "pass"` and an
> `evidence` entry whose `ref` exactly equals a command in the verify ledger the
> result is being logged against — the cycle's for a cycle agent, `closing/`'s for
> a closing agent — and that ledger's most recent entry for the command **did not exit 0** —
> a non-zero `exit_code`, **or** `exit_code: null` with `timed_out: true`, **or**
> `phase: "running"`, **or** `phase: "queued"` — `runLog` throws
> `ContradictedEvidenceError` naming the command, the recorded outcome, and the
> log path.

`null` must not be inert. A command the engine killed at the 900 s ceiling, one
still running, or one still waiting for the project verify lock records
`exit_code: null`; treating that as "no contradiction" would let a verifier log
`status: "pass"` citing a suite that never finished — or, for `queued`, one that
never started — which is the precise hole this check exists to close.

Five properties make that check safe rather than clever:

- **Exact `ref` equality only.** No fuzzy matching, no substring, no
  normalisation. An agent that runs its own command with `Bash` and names it
  differently is in exactly the position it is in today — the check adds nothing
  and takes nothing away.
- **It only ever refuses.** A green ledger entry does not make a pass. It removes
  one way to fake one.
- **It is inert where the engine ran nothing.** A cycle with no `verify/index.json`
  cannot contradict anything, which is every cycle of every project that predates
  this milestone.
- **The refusal is recoverable, and the message says how.** The check keys on the
  *most recent* entry, and any agent may call the tool: a builder that ran the test
  slot mid-cycle and got exit 1, then fixed the defect, leaves a red entry behind.
  A verifier that then sees green — through `Bash`, or through any path that does
  not append to the ledger — would have a correct verdict thrown away with no
  artefact, and `skills/mjloop-leader/SKILL.md`'s single-corrective-retry protocol
  would burn on an engine error the agent did not cause. So
  `ContradictedEvidenceError`'s message ends: *"re-run this command through
  `mjloop_verify_run` so the ledger carries a newer entry, then log again."* And
  `agents/verifier.md` requires the verifier to obtain its evidence from
  `mjloop_verify_run` whenever the slot is configured, so the ledger is not
  systematically behind the evidence it is asked to contradict.
- **The gate prover is exempt.** On the `fix` track, `reproducer` returns
  `status: "pass"` meaning *"I demonstrated the defect"*, and the command it names
  is **expected** to exit non-zero. A blanket rule would shut the fix track
  permanently. The exemption keys on `track.gate.proven_by` — data `runLog`
  already resolves at `ops/log.ts:139` — not on an agent name, because the engine
  does not know agent names. The asymmetry is already in the engine: `log.ts:154-157`
  treats a prover's evidenced pass as proof rather than as a green suite.

**The excerpt stops being a claim and becomes a citation.** `agents/verifier.md`
changes so the verifier calls `mjloop_verify_run` and builds its evidence entry
from the returned digest: `ref` is `digest.command`, and `excerpt` is built in
**this order, which is load-bearing**:

```
<failures[0].line>            ← the decisive line, first
<headline>                    ← the runner's own count line
<failures[1..]>               ← up to FAILURES_MAX, then "N more of M"
<log path>
```

The decisive line leads because `errorSignature` hashes the excerpt's *first*
line (`ops/fingerprint.ts:95-97`). Leading with `headline` was safe under the
first draft's definition only by accident, and unsafe under any definition that
could fall back to a banner. With `failures[0]` first, two cycles failing for
different reasons produce different signatures, and the repeated-error guard keeps
discriminating. When there are no failure lines — a green run cited as evidence —
`headline` leads, and a green result produces no signatures at all
(`errorSignature` returns `[]` for anything that is not a `fail`).

The output the verdict rests on is on disk, written by the engine, at a path the
agent could not have written to.

**`verify` joins `RESERVED_AGENT_NAMES` — and the honest reason is not collision.**
`runLog` always appends `.json` (`ops/log.ts:172`), so an agent named `verify`
writes `cycle-NN/verify.json`, which does not collide with the `cycle-NN/verify/`
directory at all. The same is true of `evidence` (a directory), `map` (a
run-directory `.md`) and `handoff` (a `.md`). Those four are reserved to prevent
**reader confusion** in a directory that a human, `readCycleDetail`, `writeHandoff`
and `readRunHistory` all walk. Exactly one of the five additions fixes a real
overwrite — `roster`, where an agent named `roster` genuinely clobbers
`rosterSet`'s `cycle-NN/roster.json` (`ops/roster.ts:98`) — and §15 leads with it
for that reason.

What actually keeps `verify/` and `evidence/` out of an agent list is not the
reserved name but the walk: **`readCycleDetail` (`web/read.ts:248`) filters
`.json`, and `writeHandoff` must skip directory entries explicitly.** That is
stated here rather than assumed, because the first draft used the collision
argument as a safety claim it does not support.

The rule was *no success without a verifying agent's evidence*. It becomes *no
success without a verifying agent's evidence, and the engine keeps the receipt*.

### Config surface

```ts
export const VerifySchema = z.strictObject({
  test: z.string().min(1).nullable().default(null),
  lint: z.string().min(1).nullable().default(null),
  build: z.string().min(1).nullable().default(null),
  /** Hard ceiling per invocation. The child is killed, and the kill is reported. */
  timeout_ms: z.number().int().positive().default(900_000),
  /** How long an invocation waits for the project verify lock before returning
   *  a terminal `phase: 'queued'`. Two full ceilings by default, so a waiter
   *  never gives up on a suite that is still legitimately running. */
  lock_timeout_ms: z.number().int().positive().default(1_800_000),
  /** Optional per-slot overrides for the digest's failure patterns. */
  failure_patterns: z
    .strictObject({
      test: z.array(z.string().min(1)).default([]),
      lint: z.array(z.string().min(1)).default([]),
      build: z.array(z.string().min(1)).default([]),
    })
    .prefault({}),
})
```

`verify` is declared as `VerifySchema.default({ test: null, lint: null, build: null })`
(`schemas/config.ts:103`). An earlier draft of this document claimed that adding a
field there produced a *silent runtime hole* — a config omitting `verify:` coming
back missing `timeout_ms` while typed as present. **That claim was wrong and is
retracted.** Checked against the installed zod 4.4.3 and TypeScript 5.9.2, the
edit is a **compile error**:

```
error TS2769: No overload matches this call.
  Argument of type '{ test: null; lint: null; build: null }' is not assignable to
  parameter of type '{ test: string | null; …; timeout_ms: number }'.
    Property 'timeout_ms' is missing …
```

because `.default()` takes `z.output<T>`, in which a `.default()`ed field is
required. `npm run typecheck` catches it in CI before anything ships.

The fix is still the right one, for a different and smaller reason:

```ts
verify: VerifySchema.prefault({}),
```

The literal `.default(...)` object is a **duplicate of the schema's own defaults
that the compiler forces you to maintain by hand**, and every field added to
`VerifySchema` from now on means editing two places. `.prefault({})` re-parses its
argument, so each field arrives with its own default and the duplicate is retired.
That is a maintainability argument, not a safety one, and this document should not
have dressed it as the latter. The same change is not made to `limits` or `gates`
here — one schema changes shape at a time — and §15 no longer describes them as a
trap, because they are not one.

### The trust boundary this exposes, and what closes it

`config.yaml` is hand-editable by deliberate decision
(`2026-07-27-loop-milestone-7-memory-and-extension-design.md` §5) and
`/mjloop:add track` writes it, so it is not in `PROTECTED_BASENAMES` and will not
be. An agent holding `Write` or `Edit` can therefore rewrite a verify command —
and this milestone hands that string straight to `spawn`.

The exposure is not new: the leader already types those strings into a brief and
the verifier already runs them with `Bash`. What is new is that the engine
executes them, which makes the path shorter, more direct, and worth closing.
An earlier draft of this document left it open and recorded it in §16 as a
question. **It is now closed, and the answer is the pin.**

The commands are resolved once, at `runStart`, into
`.mjloop/runs/<run>/verify-pinned.json`; `verifyRun` executes that copy and never
the live file; `verify-pinned.json` joins `PROTECTED_BASENAMES`, which the
`PreToolUse` guard already enforces by basename anywhere under `.mjloop/`; and a
run that has lost its pin refuses to verify rather than falling back. A mid-run
rewrite of `config.yaml` still parses, still shows up in the cockpit, and still
takes effect — at the next run start, where the operator expects it. What it
cannot do is change what this run executes.

Two residuals, both named in "What the engine executes" rather than left for a
reader to find: the guard matches `Write|Edit`, so `rm` through `Bash` can still
delete a pin — which is why `started_at` makes a missing pin an error rather than
a fallback; and the pin proves nothing about the *first* run in a project whose
`config.yaml` was already wrong when `runStart` read it. Pinning bounds the window
to a run boundary. It does not make a hand-editable file trustworthy, and this
document does not claim it does.

shape. A project that never calls the tool behaves exactly as it does today,
including the verifier running commands with `Bash` — the agent file changes, but
an old transcript is not replayed.

run directory gains a file retroactively. `PROTECTED_BASENAMES` gaining an entry

does not exist.

creates it. `store/lock.ts` is not modified, so every existing caller of
`withLock` — `StateStore.update`, `indexRender`, `memoryAdd`, the four in
`ops/plan.ts` — keeps its current timeouts and its current behaviour.

## 5. Idea 2 — cap `Evidence.excerpt`, `Finding.claim` and the refs

### What this is for, stated honestly

This idea saves **no model tokens**, and the first draft filed it under a
token-economy heading without checking. `mjloop_state_get` returns `StateSummary`,
whose `reproduction` is `{ proven, ref }` (`ops/summary.ts:38, 115`) — the excerpt
is not in it — and `renderSummaryLine` (`summary.ts:156-173`) does not print it.
No `cycle-NN/<agent>.json` is read into any agent's context by anything in the
engine today.

What the cap actually bounds is **`state.json`'s re-read/re-validate/re-write cost
on every subsequent `StateStore.update`**, and the cockpit's HTTP payload. Both
are disk and network. Its genuine value to this milestone is that it is what makes
idea 5's handoff and idea 1's evidence path safe to build on. It is counted at ~0
in §2's ledger, and it still ships, because a robustness fix does not need to be a
token saving to be correct.

### What exists today

```ts
export const EvidenceSchema = z.strictObject({
  kind: z.enum(['command', 'file', 'test']),
  ref: z.string().min(1),
  excerpt: z.string(),
})
```

`schemas/contract.ts:26-30`. No ceiling. Downstream, `ops/log.ts:173` writes the
parsed result verbatim to `cycle-NN/<agent>.json`, and `ops/log.ts:190-192` copies
one excerpt into `state.reproduction.excerpt`, whose schema
(`schemas/state.ts:45`) is also `z.string()`. Once there it is re-read,
re-validated and re-written by every subsequent `StateStore.update` for the
lifetime of the run, and it is in the payload of every `/api/state` response.

### The change

**Truncation must be lossless, so the ceiling and the spill are two functions in
two files, and the split is deliberate.**

In `engine/src/schemas/contract.ts` — pure, no I/O:

```ts
/** The ceiling a stored excerpt may occupy. Chosen so a failing suite's
 *  decisive output survives intact and a full transcript does not. */
export const EVIDENCE_EXCERPT_MAX = 2_000

/** A claim is a sentence. A ref is a path or a command. Neither loses anything
 *  real at these ceilings, and both are truncated in place — no spill file,
 *  because there is no plausible tail worth keeping. */
export const FINDING_CLAIM_MAX = 2_000
export const EVIDENCE_REF_MAX = 1_000

export interface ExcerptSpill { index: number; text: string }

/**
 * Bound every excerpt in a result, returning the overflow so the caller can
 * write it somewhere retrievable. `spillPath(index)` is called only for the
 * entries that overflow, so a result under the ceiling costs nothing.
 *
 * Also bounds `Finding.claim`, `Evidence.ref` and `Finding.file` in place.
 */
export function capEvidence(
  result: AgentResult,
  spillPath: (index: number) => string,
): { result: AgentResult; spills: ExcerptSpill[] }
```

**The excerpt was the largest channel into `state.json`, not the only one.**
`Finding.claim`, `Finding.file`, `Evidence.ref` and `Reproduction.ref` are
unbounded strings; `state.findings` accumulates every finding every agent files
for the whole cycle, and `state.reproduction.ref` persists for the whole run.
An agent that pastes a stack trace into `claim` reproduces exactly the cost §1
opens with, through a field the excerpt cap never touched. So `capEvidence` bounds
all of them. `claim` and `ref` take a hard ceiling with a `… (truncated)` marker
rather than a spill file: unlike an excerpt, there is nothing in their tail a
reader would ever go and fetch.

The marker replaces the tail and names the file:

```
…the last kept characters of the excerpt…
… truncated: 2000 of 18431 characters kept. Full output:
.mjloop/runs/2026-07-28-001--P001-S02--build/cycle-03/evidence/verifier--0.txt
```

In `engine/src/ops/log.ts` — the I/O half, between `parseAgentResult` and the
result write:

1. Compute the spill paths as `cycle-NN/evidence/<basename>--<index>.txt`.
2. `fs.mkdir(evidenceDir, { recursive: true })`, then write **every spill file
   first**.
3. Write `cycle-NN/<basename>.json` from the capped result.

The order is the invariant: a marker must never name a file that does not exist,
so the tail is on disk before anything points at it. If step 2 throws, step 3
never runs and the log fails loudly — the same failure mode `runLog` already has
when the cycle directory is unwritable.

**`AgentResultSchema` itself is not tightened.** No `.max()` is added anywhere.
The reason is concrete: `web/read.ts:253` re-parses historical
`cycle-NN/<agent>.json` files with the same schema, and `readJson` returning
`null` silently drops that agent from the cycle view (`read.ts:250-254`, `328-334`).
A rejecting bound would make old evidence disappear from the cockpit rather than
be shortened, which is a worse outcome than the one it prevents. The cap is a
normalisation applied on the way *in*, at `runLog`, and the schema file owns the
constant and the rule so the ceiling is legible where the shape is defined.

**One property follows, and only if the ordering is right.**

`state.reproduction.excerpt` becomes bounded **only because §14 moves the `proof`
derivation after the cap.** This does not fall out for free, and the first draft
claimed it did. `proof` is selected today at `ops/log.ts:154-157` from
`parsed.value.evidence` — *before* any cap — and `capEvidence` returns a **new**
`AgentResult`, so a `proof` derived at line 154 points at the uncapped entry and
`log.ts:191` writes the full string into `state.json` regardless. §14 therefore
pins `proof` as derived from the **capped** result, and
`'bounds the reproduction excerpt that reaches state'` is the test that fails if
that order ever regresses.

With that ordering, `state.json` cannot exceed the ceiling without a schema change
to `ReproductionSchema`. That schema
also gets no `.max()`, for the same reason — an existing `state.json` written
before this milestone may hold a long excerpt, and a state file that fails
validation on read is the one failure this system cannot recover from
(`store/atomic.ts:43-62` falls back to `.bak`, which would hold the same string).

**`errorSignature` is unaffected by *truncation*, and that is a narrower claim
than the first draft made.** It hashes `headline(excerpt)` — the first line with
digit runs collapsed (`ops/fingerprint.ts:95-97`) — and 2,000 characters is far
beyond any first line, so truncation changes no signature. The one exception is an
excerpt whose *first line* exceeds 2,000 characters, where the signature becomes
the truncated first line: still deterministic, still stable across cycles.

What the first draft did **not** analyse is that idea 1 changes what the excerpt
*contains*, which is the change that could break the guard. That is handled in §4
(the excerpt leads with `failures[0]`, and `headline` is never a banner) and
pinned in §14 (the signature is computed from the excerpt **as stored**). The two
analyses are separate and both are required.

`evidence` joins `RESERVED_AGENT_NAMES` alongside `verify` — for reader clarity,
not because a collision is possible; see §4's honest restatement of that rationale.

### Invariants

- **Lossless.** Every character an agent sent is either in the JSON or in the
  spill file the JSON names. Nothing is discarded.
- **`state.json` stays engine-owned.** The spill is a file beside the cycle's
  results, written by `runLog`, which already writes there.
- **Atomic writes are untouched.** Spill files are ordinary `fs.writeFile` into
  the cycle directory, exactly as `<agent>.json` is; only `state.json` and the
  plan manifests go through `writeJsonAtomic`.

### Tests

`engine/tests/schemas/contract.test.ts`:

- `'keeps an excerpt under the ceiling byte for byte'`
- `'truncates at the ceiling and names where the rest went'`
- `'counts characters kept and characters sent in the marker'`
- `'is idempotent, so re-parsing a capped result changes nothing'`
- `'caps every entry independently rather than the array as a whole'`
- `'bounds a claim, a file and a ref as well as an excerpt'`
- `'still accepts a historical result whose excerpt is longer than the ceiling'` —
  the compatibility test, pinning that the schema refuses nothing.

`engine/tests/ops/log.test.ts`:

- `'writes the spill file before the result that points at it'`
- `'bounds the reproduction excerpt that reaches state'` — fails if §14's ordering
  regresses and `proof` is taken from the uncapped result.
- `'produces the same error signature before and after truncation'`
- `'caps a digest-derived excerpt that exceeds the ceiling and names the verify log'` —
  the ledger match changes the *destination* the marker names, never whether the
  cap applies (§14).
- `'writes no evidence directory when nothing overflows'`

### Backward compatibility

An existing `.mjloop/` is untouched. No historical file is rewritten, no
historical file stops parsing, and the cockpit renders old long excerpts exactly
as it does now. The cap applies from the first `runLog` after the change.

## 6. Idea 3 — the verify-result cache

### What exists today

`ops/fingerprint.ts` is 97 lines, pure, synchronous, with no `fs` import and no
git invocation — and `tests/ops/fingerprint.test.ts` depends on that. It exports
`cycleFingerprint`, `errorSignature` and `errorFingerprint`, all of which
fingerprint *outputs* for the two stagnation guards. Nothing in `engine/src`
shells out to git.

### What this idea returns, restated

**It saves no tokens.** Measured green output for all three configured commands
totals well under 700 bytes; a cached digest and a fresh digest are the same size.
An earlier draft additionally prefixed a reused headline with
`reused from cycle 2 (worktree unchanged): …`, which made a hit cost *more*
context than the re-run it replaced. **That prefix is deleted** — the reuse marker
lives in the digest's `cached` / `cached_from_cycle` fields and in the ledger,
where it costs nothing and is still visible.

What it returns is **wall clock**: 1.78 s for this repository's 781-test suite,
per skipped invocation, and more on a project whose suite takes minutes. It is
kept in the milestone on that basis, and §2's ledger records it at 0 tokens and 0
by default. It is not re-argued as a context saving.

### The change

A cache hit is only ever a claim that **an identical command was run against an
identical repository and exited 0**. Everything below exists to make that claim
true or to refuse to make it. The claim is narrower than the first draft's
"identical repository" implied, and §6's exclusions now say so beside the safety
property rather than being discoverable from the tests.

**The fingerprint is computed only when `verify_cache === true`.** It is the cache
key and nothing else. Computing it unconditionally would make every verify
invocation in every project pay a full `git diff HEAD` for a feature that is off,
and the in-flight de-duplication key is a separate string that is always available
(§4).

**The input fingerprint.** Split across two files so `fingerprint.ts` stays pure:

`engine/src/store/git.ts` — new, impure:

```ts
/**
 * A digest of exactly what the working tree contains, without touching the
 * index. `null` when this is not a git repository, when git is unavailable,
 * or when any of the three commands fails.
 */
export async function worktreeDigest(projectDir: string, signal?: AbortSignal): Promise<string | null>
```

It hashes three things together. **The digest is of the project, not of the
loop's own record of the project** — `.mjloop/` is excluded from every source
below, and that exclusion is the difference between a feature that works and one
that is dead on arrival:

| Source | Why |
|---|---|
| `git rev-parse HEAD` | The committed baseline. |
| `git diff HEAD --binary --no-textconv -- . ':(exclude).mjloop/'` streamed into the hash | The exact content of every tracked modification. A status line is not enough: two different edits to one file produce the same porcelain line, and a cache that collided there would reuse a green result for code that changed. `--no-textconv` because a `.gitattributes` `textconv` or custom diff driver can make two different file contents produce identical diff bytes. |
| `git ls-files --others --exclude-standard -z -- . ':(exclude).mjloop/'` piped into a single `git hash-object --stdin-paths` | Untracked files are code too, and an untracked new module is exactly the shape of a build that must not be skipped. |

**Why `.mjloop/` must be excluded.** `initLoop` (`ops/init.ts:55-79`) creates
`.mjloop/{plans,runs,memory}`, `state.json` and `config.yaml` and **never writes a
`.gitignore` entry**. In any project that has not added one by hand, `.mjloop/` is
untracked-but-not-ignored, so every `StateStore.update`, every
`cycle-NN/<agent>.json` from `runLog` (`ops/log.ts:173`), every `roster.json`
(`ops/roster.ts:100`), and the verify logs and `verify/index.json` that `verifyRun`
itself writes all change the untracked-file set — and therefore the digest —
between cycle 1's `test` and cycle 2's `test`. The fingerprint could essentially
never repeat. This plugin's own repository ignores `.mjloop/` (`.gitignore:25`,
confirmed with `git check-ignore`), so the headline test
`'reuses a green result when the worktree has not moved'` would have passed in CI
and the feature would never have fired for a user. `tests/store/git.test.ts`
therefore includes a case over a tmp project whose `.gitignore` does **not**
mention `.mjloop/`.

**Streamed, never buffered.** `spawn` git and feed each stdout chunk into the
sha256 hash. `execFile`/`exec` default `maxBuffer` is 1 MiB, so a buffered
`git diff HEAD --binary` throws `ENOBUFS` on a large working tree,
`worktreeDigest` returns `null`, and the cache silently switches off for exactly
the repositories where it would pay. And `git hash-object --stdin-paths` is one
process for the whole list, not one per untracked file — a project mid-`npm
install`, or one without a `.gitignore` for its dependency directory, would
otherwise fork thousands of children inside the `wait_ms` budget §4 sized for the
suite itself. Above `UNTRACKED_MAX = 5_000` paths, `worktreeDigest` returns `null`
and the cache is off; that bound is documented rather than discovered.

**Submodules.** `git diff HEAD` sees only the gitlink commit and
`ls-files --others` does not descend, so a run touching a submodule's working tree
would cache straight across it. `--ignore-submodules=none --submodule=diff` is
passed to `git diff`, and a project with submodules whose diff driver defeats that
is covered by the exclusions note below.

`git write-tree` and `git stash create` are rejected: both mutate the index, and
a verification tool that alters the repository it verifies is the same category
of mistake as a verifier that edits its subject.

**What the digest does not see, stated here rather than in a test.** The safety
argument leans on completeness, so the gaps belong beside it:

- **Ignored files.** `--exclude-standard` deliberately omits everything matched by
  `.gitignore`, `.git/info/exclude` or the user's `core.excludesFile` — `.env`,
  generated code, ignored build output. A cycle that regenerates an ignored
  artefact or edits `.env` can draw a hit on a green from before it.
- **Anything outside the repository.** `node_modules`, the Node version, a running
  database, the clock. That is also why the cache is confined to one run.

A project whose build inputs live outside git must leave `verify_cache` off. That
is an acceptable limitation; an undocumented one is not, and `config.yaml`'s
comment for the key says so in one line.

`engine/src/ops/fingerprint.ts` — pure, one addition:

```ts
export function verifyFingerprint(command: string, worktree: string): string
```

`sha256` over `JSON.stringify([command, worktree])`. Two arguments, no ambient
input, so the test file's "no I/O" premise survives. `command` is the **pinned**
command (§4), which is the only one that could have run — hashing the live string
would key the cache on something the engine never executed.

**The store.** `.mjloop/runs/<run>/verify-cache.json`, an array appended by
`verifyRun`:

```json
[{ "fingerprint": "9f2c…", "slot": "test", "command": "cd engine && npm test",
   "cycle": 2, "log": "cycle-02/verify/test.log", "at": "2026-07-28T10:36:00.000Z" }]
```

Run-scoped, on disk, and therefore **not in `state.json`**. A cache in state would
be a new field the MCP server has to validate on every read and every write, for
data whose loss costs one re-run.

**What may enter the cache.** One rule, and it is the design's safety property:

> Only an invocation with `exit_code === 0`, `timed_out === false`,
> `cached === false`, a non-null fingerprint, **and a post-exit digest equal to
> the pre-spawn one** is recorded.

**The second digest is not optional, and its absence made the safety property
false.** The fingerprint is computed before the spawn; two ordinary things move
the tree while the command runs. Other agents dispatched concurrently
(`limits.max_parallel_agents`) write files. And the verify command itself writes
tracked files — `verify.build` in this repository is `npm run build`, and
`engine/dist/` is tracked and CI-asserted (§15). Without a re-digest the entry
asserts *green at D0* while the process actually observed a tree moving from D0 to
D1; the reuse then bites when a later cycle **reverts** a change — an entirely
normal loop action — putting the tree back at D0 and drawing a green hit for a
state nothing ever verified. So `verifyRun` digests again immediately after the
child exits, records a cache entry only on equality, and otherwise writes the
ledger entry (which is a record of what ran, and is always written) and no cache
entry.

**Both digests are taken inside the project verify lock** (§4). They exist to
prove the tree did not move around the child; taken outside the lock they would be
compared against a tree a second verify process was already moving, which is the
same defect as having no second digest at all, arriving by a different route. The
cache *lookup* that precedes them is deliberately outside the lock — a hit
executes nothing and needs exclusion from nothing.

A failure is never cached. A failing command is precisely what the next cycle is
trying to change, and reusing a red result would let the repeated-error guard fire
on output nobody re-produced — halting a run with *"the same verification failure
recurred"* about a defect that had already been fixed. That is the worst outcome
this milestone could produce, and the rule that prevents it is one clause.

**What invalidates a hit.** Everything, deliberately:

- One character changing anywhere in a tracked file, staged or not.
- Any untracked file appearing, disappearing, or changing content.
- A new commit, an amend, a checkout, a rebase.
- The command string changing — which folds in every edit to `config.yaml` **that
  has taken effect**, meaning one made before this run started. A mid-run edit
  changes nothing, because the pinned command is what runs and what is hashed
  (§4).
- A new run: the cache file lives inside the run directory and `runStart` creates
  a fresh one.
- `worktreeDigest` returning `null` — no git, no repository, a failed git call.
  **The cache is then off, not optimistic.** Its entire safety rests on being able
  to prove the input did not change; with no proof there is no reuse.
- A recorded log file that no longer exists on disk. A digest must be able to
  point the reader at real output, so a hit whose log has been deleted is
  discarded and the command re-runs.

**Why one run and never across runs.** A fingerprint proves the *repository* is
identical. It proves nothing about `node_modules`, the Node version, an
environment variable, a running database, or the machine. Within a run those are
constant in practice — minutes apart, same shell, same session. Across runs they
are not, and a cache that spanned a `npm install` would be reusing a result the
current environment cannot reproduce. The unit of trust is the unit the operator
reasons about.

**Default off.**

```ts
/** Whether an identical verify command may reuse an earlier green result
 *  within the same run. Off by default: see the design note. */
verify_cache: z.boolean().default(false),
```

Top-level, beside `autonomous` — a top-level boolean has no literal `.default()`
object to keep in step, so it cannot hit the trap §4 describes.

Off by default because a suite that is not a pure function of the worktree — one
that touches the network, the clock, a shared database, or a port — has flakes,
and re-running is how a loop finds them. A cache hides exactly that class of
failure, and hiding it is the opposite of what verification is for. A project
whose suite is deterministic turns it on and gets the minute back, having made
that judgement about its own suite. The engine will not make it for them.

**What the operator is told.** A hit is never silent — and never costs context to
say so.

- The digest carries `cached: true` and `cached_from_cycle: 2`. **`headline` is
  not prefixed.** Two structured booleans the reader already has cost nothing; a
  sentence prepended to the one field that ends up in an excerpt would make a hit
  more expensive than the run it replaced.
- The ledger entry for this cycle records `cached_from_cycle: 2` and points at
  the original cycle's log. The output is not copied; the engine never stores the
  same bytes twice.
- `agents/verifier.md` gains a rule: a reused result is reported in `summary` by
  name and cycle. A verdict resting on output from an earlier cycle says so.
- `handoff.md`'s verification table (§8) marks the row `reused from cycle 2`.
- The cockpit's Evidence tab shows the same marker beside the cycle's verify rows.

A cache hit does not skip verification. It skips re-executing an identical input,
which is the definition of a pure function — and where the input cannot be proved
identical, it does not skip anything.

### Tests

`engine/tests/store/git.test.ts` (new, over `makeTmpProject` with `git init`):

- `'digests a clean repository deterministically across two calls'`
- `'changes when a tracked file changes'`

### Backward compatibility

Additive and inert. `verify_cache` defaults `false`, so an existing `.mjloop/`

## 7. Idea 4 — the run-scoped map

### What exists today

`agents/scout.md` maps the ground before anyone builds on it. Its result goes to
`cycle-NN/scout.json` and its `summary` is read once, by the leader, in the turn
it arrives. `agents/builder.md:12-13` says to start from a scout map *"if a
`scout` map came with your brief"* — which today means "if the leader retyped it".
Cycle 3's builder gets nothing, so cycle 3 re-derives the layout of the code from
the code.

Two facts constrain the fix. `agents/scout.md:4` grants `Read, Grep, Glob` and
**no `Write`**, and `agents/scout.md:22-27` argues explicitly against widening
that. And the run directory is `<run_id>--<story|adhoc>--<track>`
(`ops/run.ts:27-30`) — `.mjloop/runs/<run_id>/` is not a directory and never has
been.

### The change

**The mapping agent is track data, exactly as the gate prover is.**

```ts
export const MapSchema = z.strictObject({
  /** Whose passing result becomes the run's map. */
  drafted_by: z.string().min(1),
})

// inside TrackSchema
map: MapSchema.optional(),
```

The engine does not know agent names — that is what makes a track data and lets a
new one ship without touching code (`schemas/config.ts:8-13` states this about the
gate). Hard-coding `scout` in `runLog` would be the first place the engine learned
one. `TrackSchema.superRefine` validates `map.drafted_by ∈ required ∪ available`
with the same message shape as the gate's, and `ConfigSchema.superRefine` refuses
a `drafted_by` the `specialists` map sets to `never` — a map drafted by an agent
the leader may never draft is a permanent, silent absence, which is the same
failure the gate checks exist to prevent.

`DEFAULT_TRACKS.build` gains `map: { drafted_by: 'scout' }`. No other track: the
`edit` track is one cycle and has nothing to hand forward; `fix` has a gate and a
reproduction, which is a different kind of ground truth; `plan` produces a
document.

**The engine writes it, from the agent's own result.** In `runLog`, after
`cycle-NN/<agent>.json` lands and before the state half:

```ts
if (track.map !== undefined && agent.data === track.map.drafted_by && parsed.value.status === 'pass') {
  await writeRunMap(projectDir, state, agent.data, parsed.value)
}
```

`writeRunMap` renders deterministically from data already parsed — the agent's
`summary`, its `files_touched`, and the `ref` of every `file`-kind evidence entry.
No model call, no second pass, nothing generated.

```markdown
# Map — 2026-07-28-001

**Track:** build
**Goal:** Add a health endpoint

> Sections are in cycle order. **Where two sections name the same file, the later
> one wins** — the run changes the tree it mapped.

## Cycle 1 — scout (HEAD 4b7663d)

The route table is assembled in `src/routes/index.ts` and every handler is
registered there…

- `src/routes/index.ts`
- `src/server.ts`

## Cycle 4 — scout (HEAD 6fa8c3d)

*Superseding cycle 1 for:* `src/routes/index.ts`

…
```

**Write-once, append-never-overwrite — with provenance and precedence.** If
`map.md` does not exist it is created with the header above. If it does, a
`## Cycle N — <agent> (HEAD <sha>)` section is appended. Overwriting the first map
would erase the thing this idea exists to keep.

But an append rule alone reintroduces the exact defect §12 uses to justify idea 9:
by cycle 4 the cycle-1 prose may name a file cycle 2 moved, and the first draft
said *"a second mapping pass is new information, not a correction"* while leaving
two contradictory sections with no precedence rule and a `Map:` line carrying only
a path. So three things are stamped into the document the engine renders:

- **Provenance.** Each section carries its cycle and the `git rev-parse HEAD`
  short sha it described (or `no git` when `worktreeDigest`'s first command
  fails). A reader can tell which tree a paragraph is about.
- **Precedence, in one line, in the header.** Later sections supersede earlier
  ones for any file both mention. It is stated where a model reading the file will
  see it before the prose it governs.
- **An explicit supersede list.** A later section opens with *"Superseding cycle
  N for: …"*, naming every file it and an earlier section both mention, so the
  suspect parts of the original map are visible without re-reading it.

**Bounded.** `MAP_MAX_BYTES = 8_000` and `MAP_MAX_SECTIONS = 3`. On the `build`
track (`max_cycles: 5`) an unbounded append rule is up to five unbounded sections
in a file that sits in front of every agent of every later cycle — growth
multiplied by the roster width, which is how idea 4 turned positive in §2's first
accounting. `writeRunMap` keeps the **first** section (the run's original ground
truth) and the **two most recent**, eliding the rest with
`*(cycle N elided — see cycle-NN/scout.json)*`, and truncates the whole file at
8 KB with a marker naming the drafting agent's result file. Nothing is lost: every
section is a projection of a `cycle-NN/<agent>.json` that is still on disk.

Only a `pass` writes. A scout that returns `blocked` mapped nothing.

**Reaching the brief — and the brief gets shorter, not longer.**

`skills/mjloop-contract/SKILL.md:14-23` is rendered once, here, with idea 5's line
in place too (§8), so the batch that edits it edits it once:

```
Track:      build
Cycle:      3 of 5
Goal:       <what this run must achieve>
Story:      P001-S02 | none
Map:        .mjloop/runs/<run>/map.md | none
Handoff:    .mjloop/runs/<run>/cycle-02/handoff.md | none
Verify:     test="npm test" lint="npm run lint" build=null
Return:     the loop agent contract, and nothing else
```

**Two lines are removed, and that is what makes ideas 4 and 5 net-negative.**

- **`Files:` is gone.** The map owns the run's structural file list. Carrying the
  same paths inline in every brief *and* in a file every brief points at is the
  duplication that made idea 4 cost more than it saved.
- **`Findings:` is gone from cycle 2 onward.** The handoff owns the open-findings
  list, bounded (§8). Inlining the whole `carried_findings` array into every
  agent's brief is the largest unbounded thing this design would otherwise leave
  in place: `AgentResultSchema.findings` has no ceiling (`contract.ts:37`),
  `state.findings` has none (`state.ts:62`), and forty distinct findings become a
  forty-entry line delivered to every agent of the next cycle. The leader's step 7
  changes accordingly: it hands forward the handoff path, and names in prose only
  the findings it is actually asking this agent to work.

Cycle 1 has no handoff and no map, so `Map:` and `Handoff:` read `none` and the
brief is shorter still.

`StateSummary` gains `map: string | null` — the repo-relative path when the file
exists, else null — computed with one `fs.stat`, exactly as `design_system`
already is (`ops/summary.ts:52-58`). The leader therefore learns the path from
the call it already makes, without a directory listing. `renderSummaryLine`
(`summary.ts:156`) is **not** extended: the SessionStart line is one line about
state, and a path is not news.

### Invariants

- **Scout gains no tools.** The engine writes the file from a result scout
  already returns.
- **`state.json` is untouched.** `map.md` is a run-directory artefact beside
  `HALT.md`, written on the same unlocked path `runLog` already uses for
  `<agent>.json`.
- **The gate is unaffected.** The map write sits before the gate probe and
  changes no branch of it.
- **The path defence holds.** `map` joins `RESERVED_AGENT_NAMES`, so no agent
  named `map` can produce a colliding file, and the run directory comes from
  `runDirPath` rather than from a joined string.

### Tests

`engine/tests/ops/log.test.ts`:

- `'never exceeds the map ceiling'`

## 8. Idea 5 — `cycle-NN/handoff.md`

### What exists today

`cycleAdvance` (`ops/run.ts:135-241`) already holds, inside one locked update,
everything a handoff needs except two fields: `carried` (`:163`), the sorted
`errors` (`:169`), `closedCycle` (`:170`), `input.agents`, `input.result`, and the
new state. After the lock it writes `cycle-NN/findings.json` (`:254-263`) and, on
a halt, `HALT.md` (`:332-372`). The two missing fields — each agent's `summary`
and its `files_touched` — are not in state at all. They are on disk, in
`cycle-NN/<agent>.json`.

### The change

**A new deterministic writer beside `archiveFindings`.** In `ops/run.ts`:

```ts
async function writeHandoff(
  projectDir: string,
  state: State,
  cycle: number,
  result: Result,
  agents: string[],
  carried: Finding[],
  errors: string[],
): Promise<string>
```

called from `cycleAdvance` after the lock, at `run.ts:236`:

```ts
await archiveFindings(projectDir, after, closedCycle, carried)
const handoff = await writeHandoff(projectDir, after, closedCycle, input.result, input.agents, carried, errors)
if (after.status === 'halted') await writeHaltReport(projectDir, after, cause, carried)
```

`errors` is today scoped inside the locked callback (`run.ts:169`) and must be
hoisted to a closure variable beside `carried`, `closedCycle`, `fingerprint` and
`cause` — the same hoist `cause` already documents at `run.ts:148-151`.

`closedCycle`, not `after.cycle`: the state has already incremented (`run.ts:231`),
which is precisely why `cycleDirPath` takes the cycle explicitly (`run.ts:41`).

**Where the two missing fields come from.** `writeHandoff` reads the closed
cycle's directory and parses each `*.json` with `AgentResultSchema`, **skipping
every directory entry** (`verify/`, `evidence/`) and the two aggregates
(`roster.json`, `findings.json`) — the same walk `web/read.ts:247-255` performs,
and an unparseable file is skipped rather than fatal, for the same reason. It also
reads `roster.json` for the selected list and the skip reasons, and
`verify/index.json` for the ledger. **Every one of those is optional.** A handoff
written for a cycle where nothing landed is a short handoff, not a crash:
`cycleAdvance` closes the cycle whatever happened in it, and a run must never fail
to advance because a derived document could not be assembled.

**It is written from the roster, so an omission is visible rather than silent.**
`runLog` only enters the locked update — and therefore only raises
`CycleClosedError` (`ops/log.ts:175-188`) — when a result has findings, a gate
proof, or error signatures. A `pass` carrying only `file` evidence and no findings
skips that block entirely and writes `cycle-NN/<agent>.json` against the pre-read
state, i.e. into a cycle that has just closed. An agent landing a moment late
would otherwise be absent from the table with nothing saying so, and the next
cycle would carry that document as the record of what happened. So the rows are
the roster's `selected` list, and an agent with no result file is rendered
`— no result recorded`. That is cheaper than regenerating the handoff lazily and
it matches §8's own principle: a short handoff, not a crash.

**The document, and its ceilings.**

```markdown
# Handoff — cycle 3 of 2026-07-28-001

**Result:** fail — next: cycle 4 of 5

## What each agent reported

| Agent | Status | Summary |
|---|---|---|
| builder | pass | Added the route and its test. |
| verifier | fail | One assertion still expects the old shape. |
| ui-critic | — | no result recorded |

Skipped: `security` — no auth surface touched.

## Files touched

- `src/routes/health.ts` — builder
- `test/health.test.ts` — builder

## Verification

| Command | Exit | Log |
|---|---|---|
| `cd engine && npm test` | 1 | `cycle-03/verify/test.log` |
| `cd engine && npm run typecheck` | 0 | `cycle-02/verify/lint.log` (cached, cycle 2) |
| `cd engine && npm run build` | 0 | `cycle-03/verify/build.log` (config.yaml now says `npm run bundle`) |

## Open findings

- **high** `test/health.test.ts:12` — asserts the old response shape

## Failures that could recur

- `cd engine && npm test :: N failing`
```

| Ceiling | Value | Overflow |
|---|---|---|
| `HANDOFF_MAX_BYTES` | 6 000 | truncated with a marker naming the cycle directory |
| per-agent `summary` | 200 chars | `…` |
| findings | 20, highest severity first | `*N more in cycle-NN/findings.json*` |
| files touched | 30 | `*N more in cycle-NN/<agent>.json*` |
| error signatures | 10 | `*N more*` |

**Every one of those was unbounded in the first draft**, and four of the six
sections drew on fields with no schema ceiling: `summary` (`contract.ts:35`),
`files_touched` (`contract.ts:38`), `state.findings` (`state.ts:62`) and
`cycle_errors` (`state.ts:77`). A 2 KB handoff read by a four-agent roster adds
~8 KB per cycle boundary — which is how idea 5 came out **positive** in §2's
accounting before these caps and §7's two removed brief lines.

The third row shows the two parenthetical notes the verification table carries,
both read straight off the ledger entry and neither costing a column: `cached`
with its source cycle (§6), and `live_command` when the run's pinned command and
the live `config.yaml` have diverged (§4). The second is the only place a person
who is not watching the cockpit finds out that an edit they made mid-run is
waiting for the next one.

Note what is **not** in it: the `Track:` and `Goal:` lines the brief already
carries, and the `Findings:`/`Files:` lines §7 removed from the brief because this
document now owns them. The handoff carries only what the brief does not — the
per-agent status table, the roster's skip reasons, and the verify ledger — and the
brief carries only a path to it.

Every line is a projection of data the cycle already produced. **No model call**,
which is the point: a handoff generated by a model would cost a dispatch per cycle
to summarise summaries, and would be a fourth narrative to keep honest.

`CycleAdvanceResult` gains `handoff: string | null` — the repo-relative path, and
**`null` when the write failed**. `string` contradicted this section's own "never
fatal" invariant: there is no path-shaped value for a handoff that was not
written, and `cycleAdvance`'s return value is serialised straight to the leader
(`mcp/server.ts:155-157`), where an empty string would read as a real path. `null`
is how `fingerprint: string | null` already says "this cycle produced none". It is
a plain TypeScript interface, not a zod schema, so the addition is unversioned and
costs nothing on disk.

**Written on every close, including a pass and a halt.** On a pass it is the run's
closing record. On a halt it sits beside `HALT.md` and answers a different
question: `HALT.md` says why the run stopped and what to do next
(`run.ts:318-330`), `handoff.md` says what the cycle did. Conflating them would
make each worse.

**Reaching the brief.** The `Handoff:` line in §7's template, plus
`skills/mjloop-leader/SKILL.md` step 7, which today says to fold
`carried_findings` into the next brief and will instead say to carry the handoff
path and name in prose only the findings this agent is being asked to work.

### Invariants

- **After the lock, never inside it.** A file write inside `StateStore.update`
  holds `.mjloop/.lock`, whose acquire timeout is 5 000 ms
  (`store/lock.ts:54`), against every other tool in the session.
- **Never fatal.** A `writeHandoff` failure must not roll back a state transition
  that has already committed. It is wrapped so a write error is reported and the
  advance still returns — the same reasoning `archiveFindings`'s comment gives
  (`run.ts:248-253`): losing a convenience aggregate costs nothing, because every
  fact in it is still in the per-agent files.
- **`handoff` joins `RESERVED_AGENT_NAMES`.** Reader clarity, not collision — an
  agent named `handoff` writes `handoff.json`, a different file. See §4's
  restatement of that rationale.
- **Bounded by construction.** Every section has a ceiling and every ceiling has a
  marker naming where the rest is. Nothing is discarded, and nothing grows with
  the run.

### Tests

`engine/tests/ops/run.test.ts`:

- `'writes a handoff for the cycle that closed, not the one that opened'`
- `'names every agent the roster drafted and every one it skipped'`
- `'marks a drafted agent that left no result file'` — the late-landing case.
- `'lists the files each agent touched'`
- `'carries the verification table from the cycle ledger'`
- `'notes a reused result and a diverged live command in the verification table'` —
  the two parenthetical notes, both read off the ledger entry (§4, §6).
- `'writes a handoff on a pass, a fail and a halt'`
- `'writes a short handoff when the cycle directory holds nothing'`
- `'never exceeds the handoff ceiling'` — a cycle with 200 findings, 200 files and
  a 50 KB summary.
- `'names where the elided findings went'`
- `'still advances the cycle when the handoff cannot be written'`
- `'returns null for the handoff path when the write failed'`
- `'returns the handoff path'`

### Backward compatibility

Entirely additive. Old cycles have no `handoff.md` and none is retro-generated —
a document derived from data can be regenerated, and one derived from a cycle
nobody is going to read is not worth the walk. `readCycleDetail` filters `.json`
(`read.ts:248`), so a `.md` file in a cycle directory is inert until the cockpit
opts in (§13).

## 9. Idea 6 — deduplicate `carried_findings`

### What exists today

`run.ts:163` — `carried = [...draft.findings]`. Raw. Unsorted, undeduplicated,
in whatever order concurrent agents happened to land. It becomes the return value,
`cycle-NN/findings.json` (`run.ts:262`), `HALT.md`'s open-findings list
(`run.ts:344-346`), and — via `skills/mjloop-leader/SKILL.md:279-289` — the next
cycle's task list.

The identity that would fix it already exists and is already used for exactly
this purpose: `identify` = `[severity, normaliseFile(file), claim]`
(`fingerprint.ts:50-52`), `normaliseFile` (`:58-60`), `compareIdentities`
(`:62-64`), and the sort-then-dedupe at `:41-45`. All three are module-private,
and the dedupe runs on a throwaway copy inside `cycleFingerprint`.

### The change

One export in `ops/fingerprint.ts` — and **two identities, not one**, which is the
correction that keeps this idea from destroying work:

```ts
/**
 * One entry per distinct piece of remaining work, in a stable order.
 *
 * The identity here is `(severity, normalisedFile, claim, line)` — deliberately
 * NOT `cycleFingerprint`'s. That function drops `line` on purpose
 * (`fingerprint.ts:26-30`) because it asks one question: *is this the same work
 * as last cycle?* This function answers a different one: *what work remains?*
 * — and there, two defects at line 12 and line 88 of one file are two pieces of
 * work, not one.
 *
 * Entries sharing (severity, file, claim) but differing in line are kept, in
 * ascending line order. Entries identical in all four collapse to one.
 */
export function distinctFindings(findings: Finding[]): Finding[]
```

**Why not reuse `cycleFingerprint`'s identity.** It is the obvious move and it is
wrong. `fingerprint.ts:26-30` documents the trade explicitly — dropping `line`
means *"two distinct defects sharing a severity, a file and a claim collapse into
one"* — and accepts it because the guard only asks whether the work is the same as
last cycle. Exporting that identity as the answer to *what work remains* turns an
accepted cost into lost work, and then into a false halt:

> Two genuine defects — `high`, `src/auth.ts`, "missing null check", at lines 12
> and 88 — collapse to one entry keeping the smallest line. The builder fixes line
> 12. Line 88 survives and is re-reported. The next cycle re-derives the identical
> identity set, `cycleFingerprint` is unchanged, `no_progress_count` increments,
> and the run halts with *"no progress for N consecutive cycles"* over work the
> loop was never shown.

That regression lives in `carried_findings`, `findings.json` and `HALT.md` — all
three of which this idea rewires — and asserting only that the *hash* is unchanged
would have missed it entirely, because the hash being unchanged is precisely the
symptom.

Applied in **exactly two places, both in `ops/run.ts`**:

1. `run.ts:163` — `carried = distinctFindings(draft.findings)`.
2. `run.ts:284` — the manual `halt()` passes `distinctFindings(state.findings)` to
   `writeHaltReport` rather than letting it default to `state.findings`.

The second closes an asymmetry that would otherwise be introduced: a guard halt
would print a deduplicated list and a `/mjloop:stop` would print a raw one, for
the same run, in the same file.

**Not at `log.ts:189`.** Deduplicating at accumulation was the alternative and it
is wrong for two reasons. `runLog` returns `findingsAdded`
(`ops/log.ts:202`), which would start lying about what the agent filed. And
`state.findings` is the record of what each agent actually reported — a per-agent
write under a per-agent lock, where the question is *what did this agent say*, not
*what work remains*. The cycle boundary is where the second question is asked, and
`cycleFingerprint`'s own rationale (`fingerprint.ts:20-23`) already says why the
two must not be confused: two agents reporting one defect is the same remaining
work as one agent reporting it.

**`stateSummary` follows.** `ops/summary.ts:119-120` counts severities from
`state.findings`; it counts `distinctFindings(state.findings)` instead. The count
on the status line and the list in the brief must agree, or an operator reads
`3H` and the leader hands the builder two.

### Invariants

- **The guards do not move.** `cycleFingerprint` already deduplicates internally
  (`fingerprint.ts:41-45`), so hashing a pre-deduplicated list produces an
  identical hash. `tests/ops/run.test.ts:448` — *"still strikes when a second
  agent reports the same defect"* — is about the fingerprint and still holds; it
  must be checked against `carried_findings.length`, which now differs.
- **`state.findings` is unchanged.** No dedupe is written back into state, so
  nothing about what the MCP server owns or how it validates changes.
- **`line` is preserved and discriminating.** A finding a builder must act on
  needs a line, and two lines are two pieces of work. The identity is stated in
  the function's doc comment, beside the reason it differs from
  `cycleFingerprint`'s, so the next reader does not "unify" them.
- **The two identities are allowed to differ, and a test says why.** The guard
  stays line-blind (a defect that survives a cycle usually shifts a line or two);
  the task list is line-aware (two lines are two defects). Making either follow
  the other breaks the other.

### Tests

`engine/tests/ops/fingerprint.test.ts`:

- `'collapses one defect reported by two agents into one entry'`
- `'keeps two defects that differ only in claim'`
- `'treats ./src/a.ts and src\\a.ts as one file'`
- `'keeps every distinct line of one claim'`
- `'does not drop a second defect that differs only in line'` — the regression
  test for the false-halt path above.
- `'orders identically whatever order the findings arrived in'`
- `'returns the same fingerprint before and after deduplication'` — the guard's
  identity is coarser, so collapsing exact duplicates cannot move the hash.

`engine/tests/ops/run.test.ts`:

- `'carries one entry per distinct finding'`
- `'archives the deduplicated list'`
- `'prints one line per distinct finding in the halt report'`
- `'prints the same list whether the halt was a guard or a person'`
- `'still strikes when a second agent reports the same defect'` (existing,
  updated for the new `carried_findings` length)

### Backward compatibility

No stored shape changes. Old `findings.json` archives keep their duplicates —
they are a record of a cycle that ran, and rewriting history to match a later
rule would be worse than leaving it accurate. From this change forward, archives
are deduplicated.

## 10. Idea 7 — specialist hit-rate telemetry

### What exists today

Every input is already on disk and already schema-parsed:

| Fact | File | Schema |
|---|---|---|
| drafted / skipped, with the leader's reason | `cycle-NN/roster.json` | `RosterSchema` (`contract.ts:43-48`) |
| the agent's result and its findings | `cycle-NN/<agent>.json`, `<agent>--<instance>.json` | `AgentResultSchema` |
| configured mode | `config.specialists` | `SpecialistModeSchema` |
| run identity | the directory name | `runDirName` (`run.ts:27`) |

Nothing aggregates any of it. `readRuns` (`web/read.ts:183-204`) is the only
cross-run reader and it counts cycle directories and looks for `HALT.md`.
`state.history` is reset per run (`run.ts:78`) and carries no per-agent findings,
so hit-rate cannot come from state.

### The change

**One cross-run walker, two projections.** This is the resolution of the 7/8
conflict and §14 states it again: two independent history walkers would drift.

`engine/src/ops/history.ts` — new, the **only** new cross-run filesystem reader:

```ts
export interface AgentRecord { name: string; instance: string | null; status: Result; findings: Finding[]; files: number }
export interface CycleRecord { cycle: number; selected: string[]; skipped: Record<string, string>; agents: AgentRecord[]; verify: LedgerEntry[] }
export interface RunRecord {
  id: string; run_id: string; track: string; story: string | null; halted: boolean
  cycles: CycleRecord[]
  /** The run's `closing/` directory, walked the same way. Empty when absent. */
  closing: CycleRecord | null
}

/** Newest first. Bounded — see the note on `limit`. */
export async function readRunHistory(projectDir: string, options?: { limit?: number; track?: string }): Promise<RunRecord[]>
```

`LedgerEntry` is imported from `engine/src/schemas/verify.ts`, which lands in
**batch 1** — not from `ops/verify.ts`. `readRunHistory` must parse
`verify/index.json` anyway, so it needs the zod schema, and putting the type in
the schema floor is what lets batches 2a, 2b and 2c be written in parallel (§15).

`limit` defaults to 50. Run directory names begin `YYYY-MM-DD-NNN`, so a
descending sort of the directory listing is chronological without a `stat`, and
the walk stops after `limit` runs. A cross-run walk that grew without bound would
make the Config tab slower every week the project was used, which is a defect that
arrives quietly and is blamed on something else.

`engine/src/ops/telemetry.ts` — new, a pure projection over `readRunHistory`:

```ts
export interface SpecialistRow {
  agent: string
  mode: 'auto' | 'always' | 'never' | null
  drafted: number
  skipped: number
  landed: number
  results: Record<Result, number>
  findings: Record<Severity, number>
  runs: number
  last_seen: string | null
}
export interface Telemetry {
  runs: number
  cycles: number
  /** At most TELEMETRY_MAX_ROWS (40), ordered by `drafted` descending. */
  specialists: SpecialistRow[]
  /** How many rows the cap dropped, so the ceiling is visible. */
  truncated: number
  /**
   * Drafted 5+ times with no high or medium finding. This is the ONLY field
   * `/mjloop:status` reads: the table is a report you ask for, not one you are
   * handed. See "Surfaces".
   */
  flagged: string[]
}
export async function readTelemetry(projectDir: string, options?: { limit?: number }): Promise<Telemetry>
```

Three definitions worth stating because they are what makes the number mean
something:

- **`drafted`** counts cycles whose `roster.json` selected the agent. **`landed`**
  counts cycles where its result file exists. The gap between them is a cycle the
  leader planned and the agent never returned from, which is worth seeing.
- An agent's findings come only from its **own** result file, matched
  `^<agent>(--.+)?\.json$` so instances are counted. `findings.json` is a cycle
  aggregate with no attribution and is not used here.
- The rows are the **union of every name any roster has mentioned and every name
  in any track's `closing` set**. Roster names alone would make idea 9 erase
  `docs` from telemetry entirely — a closing agent appears in no roster — and the
  "drafted 5+ times, zero high/medium findings" heuristic could never see it.
  `readRunHistory` therefore walks `closing/` alongside `cycle-NN/` (§12), and a
  closing agent's `dispatched`/`skipped` decision comes from `closing/roster.json`.
  Neither is `config.tracks` alone: the question is what actually happened,
  including for an agent since removed from a track, because removing it is often
  the decision this report informs.

**Surfaces — and telemetry is never injected into routine output.**

The first draft folded a `SpecialistRow[]` into `/mjloop:status`. This repository
ships 19 agents, so a full report is ~19 rows with two nested records each ≈ 3 KB
pushed into every status call and every Config-tab render — in a milestone whose
purpose is cutting context, for a feature whose own section concedes it is *"a
report, not a rule"*. Its only saving is second-order and human-mediated. So:

- **`commands/status.md` carries one engine-computed line and nothing else:** any
  specialist drafted five or more times with no `high` or `medium` finding to its
  name. That threshold is the whole feature — *"security drafted 12x, high/medium
  findings 0"* is an argument for a `skipped` reason, and it is not visible any
  other way. `Telemetry` gains `flagged: string[]` so that line is a field read,
  not a table scan.
- **The full table is reachable only by asking**: `mjloop_report_get` (§15 — one
  tool serving both this and §11's preflight, so the MCP surface grows by two
  rather than three) or the cockpit's Config tab. Never folded into status.
- **Bounded on the wire.** `specialists` is capped at `TELEMETRY_MAX_ROWS = 40`,
  ordered by `drafted` descending, with `truncated: number` beside it.

Telemetry is a report, not a rule. Nothing in the engine drafts or skips an agent
because of it. A specialist with a zero hit rate on this project may be the reason
the project has no security findings, and that judgement belongs to a person.

### Invariants

- **Reads only.** `readRunHistory` and `readTelemetry` open files and write
  none. They join `tests/web/read.test.ts`'s hash-everything-before-and-after
  assertion, which is the contractual test for non-destructive readers
  (`web/read.ts:14-25`).
- **Bounded.** `limit` on the walk; no unbounded array on any wire.
- **Not on the `Snapshot`.** `snapshot.ts:16-25` states the rule — the snapshot
  carries only facts already parsed from files already opened, and is
  re-serialised at ~1.25 Hz while a run is live. A cross-run walk is precisely
  what that rule excludes.
- **`ops/`, not `web/`.** `web/read.ts` is web-only and `tests/web/boundary.test.ts`
  constrains what `src/web` may import; an `ops/` module is importable by the MCP
  server and by `read.ts` both.

## 11. Idea 8 — the preflight estimate

### What exists today

Nothing anywhere in `engine/src` records a model, a token, a cost, or a duration.
`RosterSchema` has no model. `TrackSchema` has `required`, `available`,
`max_cycles`, `gate`. `HistoryEntrySchema` is `{cycle, agents, result, ref}`.
`AgentResultSchema` is `strictObject`, so an agent cannot smuggle a usage figure
in even if it knew one. The per-agent model lives in `agents/*.md` frontmatter
(`agents/verifier.md:5`), which the engine never reads.

### The change

**Two additive nullable timestamps, so a run can be measured.** Both go in
`schemas/state.ts` with the load-bearing-default comment `last_fingerprint`,
`cycle_errors` and `reproduction` already carry:

```ts
/** When the run opened. Nullable and defaulted: a state file written before
 *  this field existed must gain it on its next write rather than fail to read. */
started_at: z.iso.datetime().nullable().default(null),

// inside HistoryEntrySchema
/** When the cycle closed. Same default, same reason. */
at: z.iso.datetime().nullable().default(null),
```

`runStart` sets `started_at = now().toISOString()` inside the update it already
takes the lock for (`run.ts:62-98`). `cycleAdvance` sets `at` on the history entry
it already pushes (`run.ts:173`). No new writer, no new lock, no new file.

**`started_at` does a second job, and its doc comment says so.** Because
`runStart` is its only writer and it lands in this milestone, `started_at === null`
identifies a run that predates the milestone — which is exactly the question §4's
pin has to answer to tell a legacy run apart from one whose pin was deleted. Idea
8 needs the timestamp for an estimate; idea 1 needs it as a boundary marker; both
read the same field and neither writes it twice.

**`initialState` gains `started_at: null` in the same edit.** `initialState`
(`schemas/state.ts:101-120`) returns a `State` object *literal*, and `State` is the
output type, in which a `.nullable().default(null)` field is required — which is
exactly why `last_fingerprint`, `cycle_errors`, `last_error_fingerprint` and
`reproduction` are all spelled out there today. Without it the file does not
compile, so batch 1's file list names the constructor beside the schema.

**The estimate names no price, and that is the design.** The engine cannot see
which model an agent runs on: it is frontmatter under `${CLAUDE_PLUGIN_ROOT}/agents/`,
a directory the engine has never read and cannot reliably locate from
`projectDir`, and a project agent in `.claude/agents/` may shadow a plugin one
without the engine knowing. A currency figure built on that would be a guess
wearing an estimate's clothes, and it would be wrong within a quarter as prices
move. Shipping a price table would make this document responsible for a number
the project cannot stand behind.

What the operator gets instead is the shape of the run and what comparable runs
actually cost, in units the engine observes:

`engine/src/ops/preflight.ts`:

```ts
export interface Preflight {
  track: string
  max_cycles: number
  roster: { required: string[]; available: string[]; forced: string[]; forbidden: string[]; closing: string[] }
  /** required + available + forced, minus forbidden — the widest cycle possible. */
  dispatches_per_cycle: number
  ceiling: { cycles: number; dispatches: number }
  comparable: {
    /** How many past runs on this track the numbers rest on. 0 means no basis. */
    runs: number
    cycles: Range; dispatches: Range; minutes: Range | null
  } | null
}
export interface Range { median: number; min: number; max: number }

export async function preflightEstimate(projectDir: string, input: { track: string; story?: string | null }): Promise<Preflight>
```

It consumes `readRunHistory` (§10) and walks nothing itself. `comparable` is
`null` when the project has no completed run on that track — *no basis* is an
answer, and an invented one is not. `minutes` is `null` until `started_at` and
`at` have been recorded, so an existing project sees cycles and dispatches
immediately and durations from its next run.

Comparable means: same track, and the same *kind* of run — story-bound runs
compare with story-bound runs, ad-hoc with ad-hoc. A story is a bounded unit and a
goal typed at a prompt is not, and averaging them together produces a range wide
enough to be useless.

**The gate.**

```ts
gates: z.strictObject({
  plan_approval: z.enum(['human', 'auto']).default('human'),
  commit: z.enum(['auto', 'human']).default('auto'),
  preflight: z.enum(['human', 'auto']).default('auto'),
}).default({ plan_approval: 'human', commit: 'auto', preflight: 'auto' }),
```

Same vocabulary as `plan_approval` — *does a person decide first*. The literal
`.default(...)` object is extended in the same edit; that is a duplicate the
compiler forces you to maintain, not a trap — `npm run typecheck` refuses the
commit if you forget (§4). `gates` keeps its literal rather than switching to
`.prefault` here so exactly one schema changes shape at a time.

`auto` by default: an estimate shown before every run that then always proceeds is
a prompt nobody reads. A user who wants to approve spend sets `human`, and
`skills/mjloop-leader/SKILL.md` step 2 then requires the estimate to be reported
and confirmed before the first `mjloop_roster_set`.

**What it actually saves, stated rather than implied.** Under its `auto` default
this idea costs nothing and saves nothing: §2's ledger records it at 0. Set to
`human` it emits ~1 KB once per run and *still* saves nothing on its own — the
saving is entirely the operator's decision to trim, and it is worth naming its
size so the estimate is actionable rather than decorative:

> Removing one specialist from a track's `available` removes one dispatch per
> cycle. On this repository `agents/security.md` is 3,847 bytes, plus its brief,
> the source it reads, its result, and its tool round-trips — call it 15-40 KB
> over a five-cycle run.

`preflightEstimate` therefore reports `dispatches_per_cycle` and the ceiling as
the actionable numbers, and `commands/status.md` does not print an estimate
nobody asked for.

**Surfaces.** `mjloop_report_get` — one tool, shared with §10's telemetry, since
both are projections of one `readRunHistory` and adding two operator-facing tools
where one serves is a permanent context cost in every session (§15). Plus the
leader's step 2, and the cockpit's idle Run tab (§13) — the pre-dispatch surface,
since `runStart` is permanently forbidden from the browser (`web/writes.ts:33-47`)
and the estimate is a pure read.

### Invariants

- **Pure read, before any run exists.** `preflightEstimate` takes a track name,
  not a state; it must work when `status === 'idle'`, which is when it is asked.
- **No new write path from the browser.** The three writes stay three
  (`web/writes.ts:112`). Trimming means editing `config.yaml` or composing a
  different command, both of which already have a path.
- **`state.json` gains two nullable fields and no new writer.** Both are set
  inside updates `runStart` and `cycleAdvance` already perform.

### Tests

`engine/tests/ops/preflight.test.ts`:

- `'reports the widest cycle the track allows'`
- `'excludes a specialist set to never from the dispatch count'`
- `'includes a specialist set to always'`
- `'reports no basis for a track that has never run'`
- `'compares a story run against story runs only'`
- `'reports null minutes until a run has been timed'`
- `'names no price and no model'` — a source-level assertion that
  `src/ops/preflight.ts` contains no currency symbol and no model name, in the
  spirit of `tests/web/boundary.test.ts`.

`engine/tests/ops/run.test.ts`:

- `'stamps the run with its start time'`
- `'stamps each history entry with the time its cycle closed'`
- `'reads a state file written before the timestamps existed'`

### Backward compatibility

Both state fields are `.nullable().default(null)`, so an existing `state.json`
reads, gains the fields on its next write, and reports `null` until then — exactly
how `last_fingerprint` and `reproduction` shipped. `gates.preflight` defaults
`auto`, so an existing config's behaviour is unchanged. Historical runs contribute
cycles and dispatches to `comparable` and nothing to `minutes`.

## 12. Idea 9 — `docs` as a run-closing agent

### What exists today

`docs` sits in `DEFAULT_TRACKS.build.available` (`schemas/config.ts:211`).
`rosterSet` demands a stated skip reason for every `available` agent not drafted,
**every cycle** (`ops/roster.ts:84-89`). So a leader either drafts `docs` in cycle
2 — documenting code that cycle 4 will change — or writes four cycles of
boilerplate skip reasons. There is no post-pass hook: `cycleAdvance` returns early
on a pass (`run.ts:175-179`), and a run ends on a pass that is only known at that
moment.

### The change

**A third track set.**

```ts
// inside TrackSchema
/** Agents that run once, after the run passes — never inside a working cycle. */
closing: z.array(z.string().min(1)).default([]),
```

The map identified four knock-ons and all four are handled explicitly, because a
new set that only half the enforcement knows about is worse than no set at all:

1. **`permittedAgents`** (`config.ts:195`) becomes
   `required ∪ available ∪ closing ∪ forced`. Without this, `runLog` throws
   `UnknownAgentError` (`log.ts:128-129`) for the closing agent it was told to run.
2. **`TrackSchema.superRefine`'s `known` set** (`config.ts:34`) gains `closing`, so
   a gate may name a closing agent without tripping the "not in this track" check
   — and, more importantly, so the check keeps meaning what it says.
3. **`ConfigSchema.superRefine`** gains `closing` to its `never`-contradiction
   sweep (`config.ts:133-153`): a closing agent a specialist rule forbids is a
   documentation step that silently never happens.
4. **`rosterSet`** does two things. It does not demand a skip reason for a closing
   agent, because that is the point. And it **refuses** a closing agent in
   `selected`, with a new violation naming it: *"`docs` is a closing agent on this
   track and runs after the run passes; drafting it into a working cycle is what
   `closing` exists to prevent."* Documentation written against cycle 2's code and
   rewritten in cycle 4 is the defect, and permitting it while recommending
   against it would leave the defect.
5. **`closing/roster.json`** — the invariant, one level up. Moving `docs` out of
   `available` removes it from `rosterSet`'s *"every optional agent is either
   drafted or explained"* demand (`ops/roster.ts:84-89`), and the stated reason
   written into `cycle-NN/roster.json` is the only durable artefact of that
   decision — the one `skills/mjloop-tracks/SKILL.md:23-25` names as reviewable by
   `critic`. Deleting it with no substitute would let a run pass and ship with
   documentation silently never regenerated and nothing anywhere saying so. So
   `mjloop_roster_set` accepts a **closing roster** — `{ closing: true, selected,
   skipped }`, validated against the track's `closing` set instead of
   `available`, written to `.mjloop/runs/<run>/closing/roster.json`, and demanding
   a reason for every closing agent not dispatched. The leader's step 8 calls it
   once, and `readRunHistory` reads it (§10).

**`cycleAdvance` reports the closing set.** `CycleAdvanceResult` gains:

```ts
/** Agents to dispatch now that the run has passed. Empty on any other outcome. */
closing_agents: string[]
```

Populated only when `input.result === 'pass'` and the track declares `closing`.
On a halt it is empty: a run that did not land its work has nothing to document,
and documenting it would describe a state of the code that no longer exists.

**The sequence, fixed here, because either ordering breaks something if it is
left undefined.** `cycleAdvance` returns `closing_agents` only on a pass, at which
point the run is already `done` — and
`skills/mjloop-leader/SKILL.md` step 8 says to commit after the cycle passes,
staging the files agents reported in `files_touched`. The first draft never said
where the closing dispatch sits relative to that commit. Commit first and the
shipped commit carries stale documentation while the doc edits sit uncommitted in
a tree the run has declared done — the very defect idea 9 exists to remove,
relocated. Dispatch first and the commit contains edits no verifying agent saw.
So the sequence is stated, in §12 and in the leader's step 8:

1. `cycleAdvance` returns `pass` and `closing_agents`.
2. The leader declares the closing roster (`mjloop_roster_set` with
   `closing: true`) and dispatches the closing set.
3. Each closing agent logs through the branch below.
4. **The closing agent re-verifies.** `verifyRun`'s precondition 1 accepts
   `status === 'done'` for the run whose directory it writes into (§4), writing to
   `closing/verify/`. This is what keeps *"only verified work reaches the
   history"* true: the commit rests on a green digest taken **after** the
   documentation landed, not before it. **The widening is deliberate and
   operator-confirmed** (§16) — it was raised as a question and answered as
   wanted, not inherited by omission. It costs nothing: the closing path writes
   outside every cycle directory, files no findings, probes no gate and touches no
   state, and the pinned verify block (§4) means the re-verification runs exactly
   the commands the cycles ran.

   A widened precondition with no caller is a widening for nothing, so the grant
   goes with it: **`agents/docs.md`'s `tools:` names
   `mcp__plugin_mjloop_mjloop__mjloop_verify_run`**, following the convention
   `agents/verifier.md` and `agents/story-writer.md` already carry, and its prose
   says what it now does — write the documentation, re-run the suite through the
   engine, return the digest as evidence. That prefix hard-codes the plugin's MCP
   server id, and an install that attaches the same server under a different id
   leaves both agents holding a name that resolves to nothing, silently. The
   constraint is stated where an installer meets it, in `docs/install.md` and
   `docs/install.ar.md` (§16).
5. Then, and only then, the leader commits once — when `gates.commit` is `auto` —
   staging the closing agents' `files_touched` alongside the cycles'. A closing
   agent that returns `fail` with a red digest stops the commit: the verdict is
   untouched, because it was true of the tree the cycles verified, but the tree
   that would ship is a different one and nothing has passed against it. That is
   the one thing a closing agent decides, and it decides it about the commit
   rather than about the verdict.

`engine/tests/integration/build-cycle.test.ts` walks the whole sequence: the
closing roster, the re-verification into `closing/verify/`, the closing agent's
result citing that digest, and a commit containing the closing agent's
`files_touched`.

**Recording a closing agent's result, without touching the verdict.** This is the
one genuinely delicate part, and it is delicate because the run is already `done`.
`runLog` requires `status === 'running'` at `log.ts:114` — *before* `loadConfig` at
`log.ts:120` — and, when it proceeds, pushes findings into `state.findings`,
probes the gate, and appends error signatures. Every one of those is wrong after a
verdict: a `high` finding filed by `docs` against a run already reported as
passing would contradict a verdict nobody can revisit.

So `runLog` gains one narrow branch, keyed on **data, not a name** — and §14 places
it **before** the `status !== 'running'` refusal, because a branch placed after it
is unreachable by construction:

> After reading state and **before** the `status !== 'running'` refusal: when
> `state.status === 'done'` and `state.track !== null`, `runLog` loads config and
> the track, and if the agent is a member of that track's `closing` set it writes
> the result to `.mjloop/runs/<run>/closing/<agent>.json` and **returns**. No lock,
> no state read-modify-write, no findings, no gate probe, no error signatures. It
> returns `{ path, findingsAdded: 0, gateOpened: false }`. Otherwise it falls
> through to the existing refusal.

Two details that are easy to get wrong and are therefore stated:

- **The gate check must not run for a closing agent.** A closing agent named in
  `gate.blocks` on a gated track would otherwise be refused before the branch is
  reached. The branch returns before the gate is probed at all.
- **The branch reads state unlocked, so it must carry run identity.**
  `runLog`'s protection against a run being replaced mid-log — `RunReplacedError`
  (`log.ts:187`) — lives inside the locked update, which this branch skips. If a
  user starts the next run while a closing `docs` agent is still working,
  `runStart` sets `status: 'running'`, the branch is not taken, and docs' result
  goes down the ordinary path — where `permittedAgents` now includes `closing`, so
  the name is accepted, its findings land in the **new** run's `state.findings`,
  its signatures arm the new run's guards, and a matching `gate.proven_by` could
  open a gate. So `mjloop_run_log` takes an optional `run_id` — the one the
  closing agent was dispatched under — and the closing path **refuses with
  `RunReplacedError` when `state.run_id` differs**, exactly as the locked path
  already does. The leader passes it from `closing_agents`' own dispatch.

With the branch placed and identified, every invariant survives by construction
rather than by care:

- **Findings cannot reopen a closed run** — none are recorded.
- **The gate cannot open** — the proof probe is not reached.
- **The guards cannot be armed** — no signature is appended.
- **`state.json` is not written** — the branch returns before any
  `StateStore.update`.
- **Nothing that reads a cycle sees it** — the file is under `closing/`, not
  `cycle-NN/`, and `readRunDetail` filters `/^cycle-\d+$/` (`read.ts:213-226`).
- **It cannot be misfiled into a later run** — the `run_id` check.

For any other status, or any agent not in `closing`, `runLog` behaves exactly as
it does today — including refusing a `done` run with `NoActiveRunError`.

**Defaults.** **Every entry in `DEFAULT_TRACKS` gains `closing`, not just `build`.**
`DEFAULT_TRACKS` is declared `Record<string, Track>` (`schemas/config.ts:203`) and
`Track` is the *output* type, in which a `.default()`ed field is required — which
is precisely why all four literals already spell out `available: []` even though
`available` has a default (`config.ts:204, 207, 214, 220`). Show only `build`
gaining it and `edit`, `fix` and `plan` fail to typecheck:

```ts
edit:  { required: ['editor', 'verifier'], available: [], closing: [], max_cycles: 1 },
build: {
  required: ['builder', 'verifier'],
  available: ['scout', 'critic', 'ui-designer', 'ui-critic', 'security', 'perf'],
  closing: ['docs'],
  max_cycles: 5,
  map: { drafted_by: 'scout' },
},
fix:   { …, closing: [] },
plan:  { …, closing: [] },
```

This repository's own `.mjloop/config.yaml` needs **no** `closing: []` lines — the
schema default supplies them on read — but it does get the two-line edit moving
`docs` from `available` to `closing` under `tracks.build`. `agents/docs.md` gains a
section stating it runs once, after the run passes, against the code as it finally
stands — and the verify tool, plus the procedure for using it, per step 4 above.

**What this saves, precisely.** The per-cycle cost it removes is one skip-reason
string in `roster.json` (`ops/roster.ts:84-89`) — ~15 tokens per cycle, negligible.
The substantial saving is the **eliminated second `docs` dispatch**:
`agents/docs.md` is 3,437 bytes, plus its brief, the documentation and source it
reads, and its result — 20-60 KB. It is capped at *one* `docs` dispatch per run,
down from a ceiling of `max_cycles`, and it is **0 on a run that would have drafted
`docs` once anyway** — which `skills/mjloop-leader/SKILL.md` step 7 already
encourages by telling the leader to compose from what the findings call for rather
than out of habit. That framing also strengthens the real argument for idea 9,
which is output quality — documentation written against the code as it finally
stands — rather than tokens.

### Invariants

- **A closing agent never influences a verdict.** Structural, per the branch
  above.
- **`state.json` stays engine-owned and untouched by this path.**
- **A closing agent is still bound by the roster's other rules**, because
  `permittedAgents` includes it: a name not in any of the track's three sets is
  still refused by `runLog`.

  checked against `mcp__plugin_mjloop_mjloop__` and the suffix against the tools
  `buildServer` actually registers, which is what catches a typo, a renamed tool,
  and a server id that has drifted from the one the agents name.

### Backward compatibility

This is the one change with a behavioural default, and the answer is precise.

- **Schema:** `closing` carries `.default([])` and `TrackSchema` has no `.default()`
  wrapper of its own, so there is no literal to keep in step. An existing config
  parses unchanged and every track gets `closing: []`.
- **An existing project keeps `docs` under `available`.** `initLoop` never
  rewrites an existing config (`ops/init.ts:59-62`) and the legacy strip only
  removes keys (`store/config-store.ts:34-41`). So an existing project's `docs` behaves exactly
  as it does today — drafted per cycle, skip reason required — until a person
  moves the line. `/mjloop:status` does not nag about it, and no migration is
  attempted: rewriting a hand-editable file to change behaviour is the thing this
  project has consistently refused to do.
- The two-line edit is documented in `skills/mjloop-tracks/SKILL.md`, which is
  where a person goes to change how a track behaves.

Four ideas reach the page, and each takes the cheapest correct path.

| Idea | Reader / route | Panel | Revision to follow |
|---|---|---|---|

| 8 | `GET /api/preflight/:track` → `preflightEstimate` | Run tab's idle branch (`#run-empty`) | `${revisions.config}:${revisions.runs}` |

Three decisions are worth stating.

**The pin's drift marker and the `queued` phase need no route of their own.**
`source`, `live_command` and `phase: "queued"` are fields on `LedgerEntry` (§4),
so they arrive through the reader the Evidence tab already gains and render as two
more columns in the table that is already there. An operator who edited
`config.yaml` mid-run sees *which* command ran beside the one now in the file,
and a queued row reads as queued rather than as nothing. Both need locale keys and
neither needs an endpoint — which is the whole reason the drift was put on the
ledger entry rather than reported through a second channel.

**Telemetry follows `revisions.runs` alone, not the cycle tick.** `revisions.runs`
is the sorted run-directory listing plus that directory's own mtime
(`revision.ts:98`), so it does not move when a new `cycle-NN/<agent>.json` lands
inside an existing run. Telemetry therefore goes stale during a live run and
refreshes when the next run opens. That is the right trade: the alternative is a
full cross-run walk at ~1.25 Hz for a report whose subject is *the last fifty
runs*, and the last fifty runs do not change while one of them is in flight.

**Nothing new goes on the `Snapshot`.** `snapshot.ts:16-25` is the rule and it is
correct here: everything above has a body, and bodies are fetched.

Each new route needs a `case` in `api.ts:80-115`, a line in `api.test.ts:42`
(*"serves what the tabs read"*), the reader added to `read.test.ts:67`'s
hash-everything `Promise.all`, and — for the preflight route — validation of the
track id with `IdSchema`, not a retyped regex. Each new visible string needs a key
in `en.json` **and** `ar.json` at the same position, with every Arabic plural
category and an explicit bidi mark on any Latin run
(`tests/web/locales.test.ts:175, 183, 210`). `telemetry` and `preflight` must be
added to `NAMESPACES` (`locales.test.ts:37-64`). Cycle numbers, exit codes,
commands and paths go through `verbatim()`; "drafted {count} times" goes through
`tn()` (`lib/i18n.js:181`).

**The boundary holds structurally, not by intention.** `web/read.ts` imports the
ledger *reader* from a module that also exports `verifyRun`, so
`tests/web/boundary.test.ts` gains `verifyRun` and `worktreeDigest` to its
`FORBIDDEN` list (§4). The whole-word check is what stops a later edit importing
the executor beside the reader, and the reason travels with the entry as that file
requires.

`commands/web.md` says "five tabs" and stays true: nothing here adds a tab.

## 14. How the nine interact

The brief for this milestone named five collisions. Each is resolved by naming a
single owner, and the ownership is what the batching in §15 enforces.

### 1 and 3 both concern verify

**One executor.** `ops/verify.ts` owns spawning, the log, the ledger and the
cache. `verifyRun` consults the cache before spawning and appends to it after a
green exit; nothing else reads or writes `verify-cache.json`. A cached invocation
still writes a ledger entry — with `cached_from_cycle` set and pointing at the
original log — so `cycle-NN/verify/index.json` remains a complete record of what
this cycle's verification rested on, whether or not a process ran.

**Split by purity, not by feature.** `ops/fingerprint.ts` is pure, synchronous and
has no `fs` import, and `tests/ops/fingerprint.test.ts` assumes it. So
`verifyFingerprint(command, worktree)` — pure — goes there, and
`worktreeDigest(projectDir)` — which shells out to git — goes in the new
`store/git.ts`. Idea 3 does not put I/O into the guards' file.

**Two keys, two questions, and they are never the same string.** The in-flight
de-duplication key is `${slot}::${label}::${command}` and always exists; the cache
key is `verifyFingerprint(command, worktree)` and is `null` whenever the cache is
off or git cannot answer. Sharing one key made concurrency de-duplication
inherit the cache's nullability and the cache inherit the de-duplicator's
unpruned lifetime — two defects from one conflation (§4, §6).

**The contradiction check reads the ledger, not the cache.** A cached green entry
and a fresh green entry are indistinguishable to `runLog`, which is correct: both
assert that this command exited 0 against this worktree.

**The pin has one writer and one reader, in two different batches, sharing only a
schema.** `runStart` (2b) writes `.mjloop/runs/<run>/verify-pinned.json` once;
`verifyRun` (2a) reads it on every invocation; nothing else touches it, and
neither imports the other's module — `PinnedVerifySchema` comes from batch 1's
`schemas/verify.ts`, exactly as `LedgerEntry` does and for exactly the same reason
(§15).

**Three mechanisms guard verify, and each answers a question the others cannot.**
The pin answers *"what may this run execute?"* and is decided at run start. The
in-flight map answers *"is this same command already in flight in this process?"*
and lives as long as one child. The project lock answers *"is any verify command
executing in this project?"* and lives across processes. Collapsing any two of
them produces a defect this document has already had to name once: sharing the
map's key with the cache's gave a null key and an unpruned cross-run cache (§4);
stretching the map to cover the lock's question gives a guarantee that is false
the moment `/mjloop:web` runs two jobs; and reading the live config instead of the
pin makes all three moot, because the string being de-duplicated, cached and
serialised is one an agent could have rewritten a moment ago.

### 1 and 2 both concern evidence

**Two directories, two owners, and neither writes the other's.** `verifyRun`
owns `cycle-NN/verify/`. `runLog` owns `cycle-NN/evidence/`. Both names join
`RESERVED_AGENT_NAMES` — for reader clarity, since `<agent>.json` cannot in fact
collide with a directory (§4); what keeps them out of the agent list is that both
walks skip directory entries.

**The engine never stores the same output twice — and the cap always applies.**
A verifier that builds its evidence from a digest produces a short excerpt:
`headline` is 240 characters and `failures[]` is 20 entries. But 20 × 240 plus a
headline is ~5 KB, which is **not** under the 2,000-character ceiling, so the
first draft's claim that such an excerpt "never spills" was arithmetically wrong,
and its "skip the spill entirely" clause reopened the exact hole idea 2 closes —
including the `fix` track's copy into `state.reproduction.excerpt`
(`log.ts:190-192`). Stated unambiguously:

> `capEvidence` **always** applies. A ledger match changes only the **destination
> the truncation marker names** — the verify log instead of a fresh spill file —
> never whether truncation happens.

One command, one file. `capEvidence` remains the backstop for output an agent
typed by hand, which is every agent that is not the verifier.

**Ordering inside `runLog` is fixed here**, interleaved with what the function
actually does today rather than layered on top of it, so the four ideas that touch
it do not each assume they are first:

1. parse the name and the result (today, `log.ts:106-110`);
2. read state, unlocked (today, `log.ts:111-112`);
3. **closing branch** (idea 9) — if `status === 'done'` and `track !== null`, load
   config and the track; if the agent is in `track.closing`, check `run_id`, run the
   contradiction check of step 6 against `closing/verify/index.json`, write
   `closing/<agent>.json` and return. Otherwise fall through;
4. the existing `status !== 'running'` refusal (today, `log.ts:114`);
5. config, track, permitted, forbidden, gate (today, `log.ts:120-146`);
6. **contradiction check** against the ledger (idea 1);
7. **cap and spill** (idea 2), producing the capped result everything below uses;
8. **`proof`** — derived from the **capped** result (today at `log.ts:154-157`,
   moved);
9. **`errorSignature`** — computed from the **capped** result (today at
   `log.ts:159`, moved);
10. write `cycle-NN/<basename>.json` from the capped result (today, `log.ts:172-173`);
11. **run map** (idea 4), from the capped result;
12. the conditional locked state update (today, `log.ts:175-198`).

Four positions in that list are load-bearing and each one is a defect if moved:

- **3 before 4.** A closing agent is logged against a run whose status is `done`.
  A branch placed after step 4 is unreachable: every closing result is refused at
  `log.ts:114`. It also must sit before the gate probe (step 5), or a closing
  agent named in `gate.blocks` is refused before the branch.

  **What returning early must not skip is step 6.** The branch returns, so the
  contradiction check does not run unless it is invoked *inside* the branch, and
  once the closing agent carries `mjloop_verify_run` (§16) that omission lands
  where it costs most: the leader is told not to fetch the digest itself and to
  commit only on a green closing pass, so the closing result is the sole input to
  a permanent change and the one mechanical refusal every cycle agent meets would
  be absent from it. The check is therefore a function of the ledger and the
  directory a log path resolves against, called twice — once with the cycle's,
  once with `closing/`'s — and called before `mkdir`, so a refusal on the closing
  path leaves the same nothing behind as one on the cycle path. The gate-prover
  exemption is passed on both calls: `TrackSchema` counts `closing` as known when
  it validates `gate.proven_by`, so a project may legitimately close a track with
  the agent that proves its gate.
- **7 before 8.** `capEvidence` returns a *new* `AgentResult`. A `proof` derived
  from the uncapped result points at the uncapped excerpt, and `log.ts:191` writes
  the full string into `state.json` — the failure §1 opens with. §5's test
  `'bounds the reproduction excerpt that reaches state'` fails if this regresses.
- **7 before 9.** The pin is: **signatures are computed from the excerpt as
  stored.** `cycle_errors` and `HALT.md` then always cite text that is on disk, and
  a forensic reader can reproduce the guard's input from the run directory. The
  first draft's list omitted `errorSignature` entirely, leaving both readings
  available — one where the guard hashes text that exists nowhere, one where its
  input silently changes shape with no test pinning it. §5's
  `'produces the same error signature before and after truncation'` becomes a real
  assertion rather than an assumption, and §4's
  `'two different failures of one command produce two signatures'` guards the
  other half.
- **6 before everything that writes.** The contradiction check must refuse before
  any artefact exists, which is the negative-space property
  `tests/ops/log.test.ts:86-91` already asserts for every other refusal.

### 4 and 5 are both run-scoped artefacts

**Different levels, different writers, no shared field.** `map.md` is
run-directory, written by `runLog` on the mapping agent's pass. `handoff.md` is
cycle-directory, written by `cycleAdvance` after the lock. Neither reads the
other's file.

**They share two prose files and therefore one owner.** Both add a line to
`skills/mjloop-contract/SKILL.md:14-23` and both change the leader's compose and
fold-forward steps. The brief template is rendered once, in §7, with both lines
in place **and the two lines they replace removed**, so the batch that edits it
edits it once and the net change to every brief is negative.

**`StateSummary` gains `map` and not `handoff`.** The map is a run-level fact the
leader needs at compose time and would otherwise have to `stat` for; the handoff
path is `cycleAdvance`'s return value, which the leader is holding when it
composes the next brief. Adding both would put a derivable string on every
agent's summary payload for no gain.

### 5 and 6 both concern findings

**Deduplication happens once, at `run.ts:163`, before anything consumes
`carried`.** `writeHandoff` receives `carried` and does not deduplicate again;
neither does `archiveFindings`, nor `writeHaltReport`. `distinctFindings` is
called in exactly two places, both in `ops/run.ts` — the cycle close and the
manual halt — and that is stated in its doc comment so a third call site is a
visible mistake rather than a silent double-application.

`cycleFingerprint` is *not* changed to consume the deduplicated list; it keeps
deduplicating internally, on its own coarser, line-blind identity. `distinctFindings`
is line-aware (§9). The two identities are deliberately different because they
answer different questions, and because `distinctFindings`'s is strictly finer,
feeding it into `cycleFingerprint` still produces the same hash — a test asserts
it. Unifying them would either blind the task list to a second defect in one file
or let a flailing loop escape every strike.

### 7 and 8 both read history

**One walker, two projections.** `ops/history.ts` is the only new cross-run
filesystem reader. `ops/telemetry.ts` and `ops/preflight.ts` both consume
`readRunHistory` and neither calls `fs` directly. Two independent walkers would
disagree about what a run is — whether a halted run counts, whether an unparseable
roster skips the cycle or the run, where the `limit` falls — and they would
disagree quietly, in two reports the operator would compare.

**They read different fields of the same record and share none.** Telemetry uses
`CycleRecord.selected`, `.skipped` and `.agents[].findings`. Preflight uses run
counts, cycle counts, dispatch counts and the two new timestamps. Neither writes.

**The two timestamps have one writer each.** `started_at` is set only by
`runStart`; `HistoryEntry.at` only by `cycleAdvance`. Both inside locked updates
those functions already perform, so no new lock is taken anywhere.

### One more, unnamed but real: 1 and 9 both change `runLog`

Together with 2 and 4, four ideas modify `ops/log.ts`. The step order above is the
resolution, and §15 puts all four in one batch under one agent. `runLog` carries
the reproduction gate, the roster enforcement and the only path from an agent's
claim into the run's state; it is the last function in this system that should be
edited by four agents holding four partial pictures.

### Batch 5 — prose, defaults and the shipped bundle (three agents)

**5a — skills and commands.** `skills/mjloop-leader/SKILL.md`,
`skills/mjloop-contract/SKILL.md`, `skills/mjloop-state/SKILL.md`,
`skills/mjloop-tracks/SKILL.md`, `commands/status.md`, `commands/build.md`.

Five of those edits are the prose half of a control the engine cannot enforce, and
none is optional:

- **`SKILL.md`, What you never do:** *"Never call `mjloop_verify_run` yourself"*
  (§4). The engine cannot see caller identity.
- **`SKILL.md` step 7:** carry the handoff path; do not inline
  `carried_findings` (§7, §8).
- **`SKILL.md` step 8:** the closing sequence — declare the closing roster,
  dispatch, let a closing agent re-verify, **then** commit once, staging the
  closing agents' `files_touched` too (§12).
- **`skills/mjloop-state/SKILL.md`:** `verify-pinned.json` is a run-directory
  artefact written once by `mjloop_run_start`, protected by basename like
  `state.json`, and read by `mjloop_verify_run` — so an edit to `config.yaml`'s
  `verify:` block takes effect at the **next** run start (§4). That file is where
  a person goes to find out who owns a write, and a protected file it does not
  mention is a file someone will try to edit.
- **`commands/status.md`:** the single `flagged` line only; never the telemetry
  table (§10).

**5b — agents and this project's own config.** `agents/verifier.md`,
`agents/scout.md`, `agents/builder.md`, `agents/docs.md`, `.mjloop/config.yaml`.

`agents/verifier.md` carries five rules, all of which the engine relies on and
none of which it can check: build the excerpt with `failures[0]` first; obtain
evidence from `mjloop_verify_run` rather than `Bash` whenever the slot is
configured; a `phase: 'running'` **or `phase: 'queued'`** digest is never a `pass`
— a queued one is a reason to call again, not a reason to reach for `Bash` and
run the suite the lock was holding back; report a `cached` result by name and
cycle in `summary`; and report a digest carrying `live_command` in `summary` too,
naming both strings, because a run whose config has moved under it is something a
person should be told once rather than discover in a diff. `.mjloop/config.yaml`'s only edit is moving
`docs` from `available` to `closing` under `tracks.build` — no `closing: []` lines
are needed anywhere, since the schema default supplies them on read.

**5c — the shipped bundle.** `engine/dist/**`, `.claude-plugin/plugin.json`,
`engine/package.json`, and the milestone plan under `docs/superpowers/plans/`.

**One rule makes 5c possible: no earlier batch runs `npm run build`.**
`engine/dist/` is committed and CI asserts it matches a fresh build
(`.github/workflows/ci.yml`), and `scripts/build.mjs` copies the whole of
`src/web/public` — 36 tracked files — verbatim into a `dist/` that holds 42 tracked
files in all, so two agents running the build would collide on every one of them.
5c rebuilds once, after every `engine/src` change has
landed, and commits `dist/` with the version bumps. The consequence is stated
plainly: intermediate commits in batches 1 through 4 leave `engine/dist/` stale
and would fail CI's `git diff --exit-code -- engine/dist` on their own. The
milestone lands as one pull request, and only its final commit is a shippable
tree.

## 16. Decisions

| Decision | Chosen | Rejected |
|---|---|---|
| Who runs verify | The engine, reporting facts | The engine deciding a verdict — an exit code is not a judgement about this project |
| Verify beyond the client timeout | `phase: 'running'` plus in-process attachment | Blocking past 60 s, which kills the request; or spawning twice, which runs two suites |
| Which commands the engine executes | The run's **pinned** copy — resolved by `runStart` into `verify-pinned.json`, which joins `PROTECTED_BASENAMES` | The live `config.yaml` at call time, which any agent holding `Write` can rewrite between the brief and the spawn; or protecting `config.yaml` itself, which milestone 7 deliberately left hand-editable and `/mjloop:add track` writes |
| What gets pinned | The whole resolved `verify` block, re-parsed through `VerifySchema` | The three command strings alone — `timeout_ms` and `failure_patterns` are executed policy too, and a restated schema is one more literal to keep in step |
| A run with no pin | Live config **only** when `started_at === null`; on any newer run a missing or unparseable pin is an error | Falling back whenever the file is absent, which would make `rm` the downgrade attack the pin exists to prevent |
| Config drift during a run | Reported — `live_command` on the digest and in the ledger — and never obeyed | Refusing to run, which hands any agent holding `Write` a way to halt the run; or silence, which leaves an operator's edit looking applied |
| Concurrent verify across processes | A project-scoped lock, reusing `store/lock.ts` **unchanged** | The in-flight map, which is one process wide; a per-slot lock, which serialises perfectly and collides anyway when two slots share a port; a new lock primitive beside one already argued out in comments |
| Verify lock staleness | Derived: `verify.timeout_ms` + 60 s, never configured | A configured value, which can be set below the ceiling and then reclaims the lock out from under a suite that is still legitimately running |
| A waiter that cannot take the lock | `phase: 'queued'`, a ledger entry, and the wait continues in the background | `phase: 'running'`, when no child of that call is running; or blocking, which is the failure `wait_ms` exists to avoid |
| Re-verifying a run that is `done` | Accepted, into `closing/verify/` — operator-confirmed | Refusing, which ships a commit whose last green digest predates the documentation inside it |
| Excerpt cap | Normalise at `runLog`, spill to a file | `.max()` on the schema — it would make historical evidence vanish from the cockpit rather than shorten it |
| Digest extraction | A skip list, a summary-shaped `headline`, configured failure patterns | "the first non-empty line", which on all three of this repo's commands is npm's script echo — constant across green and red, and fatal to `errorSignature` |
| Where the signature comes from | The excerpt **as stored**, leading with `failures[0]` | The excerpt's first line whatever it is, which a banner would make constant per command |
| In-flight de-duplication key | `slot::label::command`, pruned when the child settles | The cache fingerprint, which is null by default and never pruned — an unconditional cross-run cache of failures |
| Cache key | `git rev-parse HEAD` + `git diff HEAD --binary --no-textconv` + untracked content, all excluding `.mjloop/`, and re-checked after the child exits | `git status --porcelain`, where two different edits share a line; `git write-tree`, which mutates the index; a pre-spawn-only digest, which asserts green for a tree the process never saw |
| Findings identity | Two: line-blind for the guard, line-aware for the task list | One shared identity, which loses a second defect in one file and then halts the run for "no progress" over work it never showed anyone |
| Telemetry delivery | One line in status; the table only when asked | A `SpecialistRow[]` folded into every `/mjloop:status` |
| New MCP tools | Two — `mjloop_verify_run`, `mjloop_report_get` | Three; the surface is a permanent per-turn cost and two projections of one walk do not need two tools |
| The brief | Loses `Files:` and `Findings:`; gains `Map:` and `Handoff:` | Gaining two lines while adding two documents that repeat them |
| Cache scope | One run | Across runs, where `node_modules` and the environment are not the same repository |
| Cache contents | Green results only | Caching a failure, which would let the repeated-error guard halt a run over a defect already fixed |
| Cache default | Off | On — a suite that is not a pure function of the worktree has flakes, and re-running is how a loop finds them |
| Who writes `map.md` | The engine, from the mapping agent's own result | Widening `scout`'s tools, which `agents/scout.md:22-27` argues against; or a second model call to generate it |
| Which agent maps | `tracks.<n>.map.drafted_by` | Hard-coding `scout` — the engine does not know agent names, and that is what makes a track data |
| Map on a second draft | Appended under a cycle heading | Overwritten, which erases the ground truth later cycles read |
| Handoff | Deterministic, from files the cycle already wrote | A summarising model call per cycle — a fourth narrative to keep honest |
| Where findings deduplicate | `run.ts:163` and the manual halt | `log.ts:189`, where `findingsAdded` would start lying about what the agent filed |
| Telemetry and preflight | One `readRunHistory`, two projections | Two walkers, which would disagree quietly about what a run is |
| Cost estimate | Cycles, dispatches, minutes | A currency figure built on frontmatter the engine cannot read and prices that move |
| Preflight gate | `gates.preflight`, default `auto` | Default `human` — an estimate shown before every run that always proceeds is a prompt nobody reads |
| Closing agents | A third track set, refused inside a working cycle | Leaving `docs` in `available` with a per-cycle skip reason, which is four cycles of boilerplate around one real decision |
| A closing agent's result | Written to `closing/`, no state touched | Through the normal `runLog` path, where a `high` finding would contradict a verdict nobody can revisit |
| Contradicted evidence on the closing path | Checked, against `closing/verify/index.json`, inside the branch before it writes | Skipped as a side effect of the early return — which leaves the one result the commit decision rests on as the one result nothing checks |
| Who calls the widened precondition | `docs` itself — its `tools:` grants `mjloop_verify_run` | Leaving `docs` unable to verify, which is a widening with no caller and a commit whose last green digest predates the documentation inside it |
| Naming an MCP tool in an agent | The plugin's server-id prefix, as `agents/verifier.md` and `agents/story-writer.md` already do — with the constraint documented in `docs/install.md` and `docs/install.ar.md` | Inventing a portable spelling the harness does not resolve; or leaving the constraint undocumented, where an install under another server id drops the tool with no error anywhere |
| Migration | None; defaults are safe and behaviour changes are opt-in | Rewriting a hand-editable config to change behaviour |

## 17. Reviewed and rejected

Three adversarial reviews raised 38 findings against the first draft of this
document. Thirty-five are folded into the sections above, including all fourteen
high-severity ones. Three recommendations are declined, and the reasons are here
rather than absent.

**"Remove idea 3 from this milestone, or re-justify it on latency."** — *economics,
idea 3.* The finding's analysis is accepted in full and §6 is rewritten around it:
the cache cuts zero tokens, the `reused from cycle N` headline prefix was net
context-positive and is deleted, and `verify_cache` defaults false so the measured
saving for every existing project is zero. What is declined is the removal. The
alternative offered — re-justify on latency — is what §6 now does, and 1.78 s per
skipped invocation on this repository is a real return on a project whose suite
takes minutes. It ships with its cost counted at 0 tokens in §2's ledger, which is
the honesty the finding was asking for.

**"Keep the MCP surface at 17 — serve telemetry and preflight through the
cockpit's read API only."** — *economics, cross-cutting.* The cost accounting is
accepted and §2 now counts it. The prescription is not reachable: the leader needs
the preflight estimate when `gates.preflight` is `human`, and `/mjloop:status` is a
slash command executed by a model — neither can make an HTTP request to the
cockpit, which may not be running. Folding either onto `StateSummary` would put a
cross-run walk behind `mjloop_state_get`, which is called constantly. The surface
therefore lands at **18**, not 17 and not 19: `mjloop_verify_run`, plus one
`mjloop_report_get` serving both projections of the single `readRunHistory` walk
that §14 already insists on. That is the smallest number that works.

**"Re-scope the milestone around ideas 1, 6 and 9; defer ideas 5 and 7."** —
*economics, cross-cutting.* The measured ranking is accepted, and it drove the
largest changes in this revision: idea 6 moves to batch 1 and is named as the
milestone's test, idea 4 gains a hard cap, idea 5 is capped and the brief loses
the two lines the handoff now owns, idea 7 is removed from routine status output.
What is declined is deferral. Both fix defects a later milestone would inherit:
without the handoff there is no durable record that a drafted agent left no result
(§8), and without telemetry the `available` lists nobody prunes keep costing a
dispatch per cycle forever. Bounded, both are net-negative or zero in §2's ledger,
which was the standard the finding proposed. An idea that is wrong is dropped; an
idea that was unbounded is bounded.

## 18. After this

The run stops regenerating itself. A cycle opens with a map it did not draw, a
handoff it did not write, a findings list already reduced to distinct work, and a
verification result the engine executed and can still show you. The verdict is
still an agent's, and it is now the only thing in the loop that a model produces
from scratch every time — which is where the judgement belongs.
